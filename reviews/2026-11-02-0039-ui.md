# Deep review: `src/skills_overhaul/ui/` (2026-11-02-0039)

Scope: every file in `src/skills_overhaul/ui/` (7 files, 2,884 lines), the stray tracked binary `skills_overhaul/ui/CharacterTabReplacer.class`, the tree data in `data/config/skills_overhaul/trees/*.json`, and the code the UI calls across its boundary: `level/GameSpend`, `level/SpendService`, `level/RespecRunner`, `level/RespecService`, `basics/ActiveLaneService`, `tree/PrereqValidator`, `tree/Node`, `tree/TreeRegistry`, `SkillsOverhaulModPlugin` (where the UI is registered).

Build: **not compiled.** `build.sh` hard-codes `GAME_DIR="/home/jayden-eppcohen/Games/Starsector"` for `starfarer.api.jar` and the other game jars. Those jars are not in this container, so neither `./build.sh` nor `./build.sh test` can run here.

## Verdict

The character-tab UI is the only path players use to spend points, and it enforces purchase rules that the authoritative purchase path (`GameSpend.purchase`) does not. Three of those rules can be bypassed or computed wrongly. The three most valuable fixes:

1. **Move the "needs a node in the previous tier" rule out of the UI and into `GameSpend`/`PrereqValidator`.** Today you can bypass it by un-pending the node that satisfied it (B1).
2. **Make the UI budget check use the same pool-lock rule as `SpendService`.** At the moment Confirm can buy part of the pending set, report nothing, and discard the rest (B2).
3. **Gate Respec on story points and show its real cost.** At the moment Respec runs with 0 SP (B3).

Everything else is either dead code (around 400 lines) or per-frame work and fragility in the reflection-based mount.

## Blocking

### B1. Tier gate is enforced only at click time and can be bypassed by un-pending

`src/skills_overhaul/ui/CharacterTabPanelPlugin.java:1223`
```java
        if (!hasAnyInPreviousTier(clicked.getTier(), def, snap, pending)) return;
```
`src/skills_overhaul/ui/CharacterTabPanelPlugin.java:1282-1284`: un-pending removes only dependents that list the removed node in their prereqs:
```java
                for (String pre : n.getPrereqs()) {
                    if (toRemove.contains(pre)) {
                        toRemove.add(id);
```
`src/skills_overhaul/level/GameSpend.java:28`: the commit path checks prereqs only:
```java
        if (!PrereqValidator.canPurchase(def, m, nodeId)) return false;
```

**Failure scenario:** in `pilot_defense.json`, every tier-2 node except `so_defense_fortress_shield` has `{"all": ["so_defense_hull_conditioning"]}`, which is the tier-0 root (for example `so_defense_fortify`, y=2). Steps, with the root owned:

1. Click `so_defense_reinforced_plating` (tier 1). It becomes pending.
2. Click `so_defense_fortify` (tier 2). It passes `hasAnyInPreviousTier` because of the pending tier-1 node.
3. Click `so_defense_reinforced_plating` again to un-pend it. `fortify` stays pending because its prereq is the root, not the tier-1 node.
4. Confirm. `GameSpend.purchase` buys `fortify` with no tier-1 node owned.

The same shape exists in `pilot_gunnery`, `pilot_maneuvering` and `pilot_systems` (21 pilot nodes in total whose prereqs skip the previous tier), and in every admin `_t5` capstone, whose prereq is `_t0`. Any caller of `GameSpend.purchase` other than the UI also skips the gate.

**Fix:** move the previous-tier rule into `PrereqValidator.canPurchase` and `canPurchaseWithPending`, so both the UI and `GameSpend` enforce it. In `removePendingWithDependents`, after the prereq cascade, repeatedly drop any pending node whose tier gate no longer holds. Alternatively, express the tier requirement as explicit prereq clauses in the JSON.

### B2. Pending-budget check ignores the migration-pool lock, so Confirm partially commits and drops the rest silently

`src/skills_overhaul/ui/CharacterTabPanelPlugin.java:1227-1231`
```java
        int migLocked = (int) f(snap.get(migLockedK));
        int migPool   = (int) f(snap.get(migPoolK));
        int freeUni   = (int) f(snap.get(freeUniK));
        int totalPts  = treePts + migLocked + migPool + freeUni;
        if (sumPendingCost(pending) + clicked.getCost() > totalPts) {
```
`src/skills_overhaul/level/SpendService.java:32-33`: the real spend refuses the pool when it is locked to another tree:
```java
        String lockedTo = (String) mem.get(POOL_LOCK_KEY);
        boolean canUsePool = (lockedTo == null || lockedTo.equals(tree.name()));
```
`src/skills_overhaul/ui/CharacterTabPanelPlugin.java:1262-1268`
```java
            if (!ok) {
                Global.getLogger(CharacterTabPanelPlugin.class).warn(
                        "[SkillsOverhaul/UI] purchase failed for " + nodeId);
                break;
            }
        }
        pending.clear();
```

**Failure scenario:** the migration pool is locked to `PILOT` and has 3 unallocated points. The player opens COMMANDER with 1 tree point. The UI counts 1 + 3 = 4, so it lets the player pend four cost-1 nodes and shows "Confirm (4 pts)". On Confirm:

- The first purchase succeeds.
- The second fails because `SpendService` will not use the PILOT-locked pool.
- The loop breaks and `pending.clear()` discards the other selections.

The player sees one node bought, gets no message, and keeps a point allocation they did not choose.

**Fix:**
- Skip `migPool` when `POOL_LOCK_KEY` is set to another tree. The snapshot also needs to carry `SpendService.POOL_LOCK_KEY`, which it currently does not include.
- Better: dry-run the whole pending set through `SpendService.spend` on a copied snapshot, both when pending a node and before committing.
- On commit, surface failures with `Global.getSector().getCampaignUI().addMessage`, and keep the unbought nodes pending instead of clearing them.

### B3. Respec runs with zero story points

`src/skills_overhaul/ui/CharacterTabPanelPlugin.java:963-966`
```java
            if (ownedCountForTree(currentTree) > 0) {
                SkillUISounds.playRespecReset();
                skills_overhaul.level.RespecRunner.run(currentTree);
                rebuild();
```
`src/skills_overhaul/level/RespecRunner.java:80-83`: the charge is unconditional and its result is never checked:
```java
        if (r.storyPointsCharged > 0) {
            MutableCharacterStatsAPI stats = Global.getSector().getPlayerPerson().getStats();
            stats.spendStoryPoints(r.storyPointsCharged, false, null, false, "Skills Overhaul respec");
        }
```

**Failure scenario:** after the first free respec of a tree (`RespecService.java:28-29`), a player with 0 story points clicks "Respec (1 SP)". Every point is refunded and the tree is wiped, even though the player could not pay. Repeat as often as you like: unlimited free respecs. Depending on how `spendStoryPoints` handles a balance that is too small, which could not be checked without the game jar, the SP count may also go negative.

**Fix:** in the button handler and in `RespecRunner.run`, refuse when `respecUsedKey(tree)` is set and `getStoryPoints() < 1`. Disable the button with the same check in `paintLeftRail`. Label the button "Respec (free)" when the tree's first respec is still unused (see A12).

## Advisory (ranked)

1. **"Unlockable" state disagrees with what a click accepts.** `PathTreeBuilder.java:639-641` (`isUnlockable = !isOwned && !isPending && PrereqValidator.canPurchaseWithPending(...)`) ignores the tier gate (`CharacterTabPanelPlugin.java:1223`) and the budget (`:1231`). Nodes drawn blue with "Unlockable (cost n)" in the tooltip can silently ignore clicks; the only trace is a `warn` in `starsector.log`. Compute "unlockable" with the same validator the click uses, and play a deny sound or show a message on refusal.
2. **`canSwapLive()` may permanently block T0 active-slot swaps (could not verify).** `ActiveLaneService.java:33-34` returns `canSwap(Global.getCombatEngine() != null)`. The UI only exists in the paused campaign. If `Global.getCombatEngine()` keeps its last engine after a battle (a common pattern in mods, not checked here), `CharacterTabPanelPlugin.java:1172-1174` returns silently on every click. Check `Global.getCurrentState() == GameState.COMBAT` instead.
3. **The T0 swap displaces `active.get(0)` from any tree.** `CharacterTabPanelPlugin.java:1187`: `String displaced = active.get(0);`. The active-basics list is global across PILOT, COMMANDER and ADMIN (`MAX_ACTIVE = 2`). Clicking a Commander T0 can quietly deactivate a Pilot basic that is not on screen. There is a TODO for this; at minimum, prefer a slot from the current tree and say which basic was displaced.
4. **A failed install retries every frame with a full UI-tree crawl and warn logs.**
   - `CharacterTabReplacer.advance` calls `install()` every frame while the Character tab is open and `installed` is false.
   - Each early return (`CharacterTabReplacer.java:103-105`, `:116`, `:119`) leaves `installed` false.
   - `ReflectionUtils.invoke` logs a `warn` on every call to a missing method (`ReflectionUtils.java:89`, `"[ReflectionUtils] method not found: "`), even though `findMethod` caches the miss.
   - Only the `Throwable` path is limited to one warning (`reflectionWarned`).

   On a game build where discovery fails, the log grows by several lines per frame and the recursive `findLargestPanelWithCanReassign` crawl runs 60 times a second. Latch a "discovery failed" flag until the tab changes.
5. **The restore path can add the vanilla panel twice.** When `p.removeComponent(target)` throws, the panel is only hidden (`CharacterTabReplacer.java:158-166`). `maybeUninstall` still runs `vanillaParent.addComponent(vanillaPanel)` (`:299`), which adds it a second time to a parent that already holds it. Record whether removal succeeded, and only re-add if it did.
6. **`hasMethodOfName` does not match its contract.** `ReflectionUtils.java:103`: `/** True iff target's class (or superclasses) declares a method of this name. */`. The body only scans `clazz.getDeclaredMethods()` (`:111`). If a future game build moves `canReassign` to a superclass, the vanilla panel is never found and the mod quietly falls back to the vanilla tab. Walk `getSuperclass()` the way `findMethod` does.
7. **Per-frame rebuild of edges and prereq checks in `renderBelow`.** `CharacterTabPanelPlugin.java:494-496` calls `PathTreeBuilder.refreshEdgesAfterLayout(panel, this)` every frame. That re-reads every purchased flag from memory and, for every edge, allocates a snapshot map and runs `PrereqValidator.canPurchaseWithPending` (`PathTreeBuilder.java:713-714`). That is about 106 nodes and their edges on the Commander tab, every frame. `drawNodeIcon` also calls `Global.getSettings().loadTexture(path)` for every node every frame (`CharacterTabPanelPlugin.java:830`). Whether the engine caches that call could not be checked; if it does not, this is disk I/O per frame. Build edge colours once in `rebuild()`, refresh only the geometry, and load textures once at attach.
8. **The scroll-wheel hit area is shifted upward.** `CharacterTabPanelPlugin.java:1109-1110` accepts `my >= viewY - SCROLL_H - 4f && my <= viewY + viewH`, a band above the viewport. The scrollbar is drawn below it, at `trackTop = py + viewY + viewH + 2f` (`:769`). The wheel does nothing over the scrollbar. Use `my >= viewY && my <= viewY + viewH + SCROLL_H + 4f`.
9. **Every wheel tick and every click runs a full `rebuild()`.** Each rebuild tears down and recreates all UI elements, including one hit TooltipMaker per node (`:1119`, `:1160`, `:1238`), and logs two `info` lines (`:135`, `:234`). Scrolling only changes `sx`; re-`inTL` the existing hit rects instead.
10. **Dead code, about 400 lines:**
    - `NodeIconPanelPlugin.java`: the whole file has no references.
    - `PathTreeBuilder.configureForViewport(TreeDef, …)` (`:94-225`): only the `List<TreeDef>` overload is called.
    - `resolveTreeOf` (`:780`).
    - The 6-argument `refreshEdgesAfterLayout` (`:501-506`).
    - The deprecated 4-argument `ConnectionLineDrawer.draw` (`:80-83`).
    - `laneColumns`: filled by `buildPaths` and never read.
    - All merge/sublane handling (`emitSublaneColumn`, merge colours, stipple-by-merge). `Node.isMerge()` is hard-coded `return false;` and `Node.getLane()` returns `"default"` (`tree/Node.java:42,44`), so this code cannot run.
11. **A stale binary is tracked in git.** `skills_overhaul/ui/CharacterTabReplacer.class` is committed at the repo root, even though `.gitignore` has `*.class`; it was last touched in `3a40538`. It is not on the mod classpath (`jars/SkillsOverhaul.jar` is), but it ships in any zip of the repo and does not match the source. Run `git rm` on it.
12. **Respec UX:**
    - The label is always `"Respec (1 SP)"` (`CharacterTabPanelPlugin.java:436`), but the first respec of each tree is free (`RespecService.java:28-29`).
    - One click wipes the whole tree with no confirmation.
13. **A debug string ships in the player-facing bottom bar.** `CharacterTabPanelPlugin.java:484`: `+ "            " + UI_VERSION;` renders "V17-EVENT-HIT-FIRST" next to the XP line. Log it; do not paint it.
14. **One full-volume sound per node on commit.** `GameSpend.java:42` (`SkillUISounds.playTierSkillSound(tree, n.getTier(), 1f);`) runs inside the commit loop at `CharacterTabPanelPlugin.java:1260-1261`, so confirming six nodes plays six overlapping sounds. Play one sound after the loop.
15. **The memory key is duplicated as a literal.** `CharacterTabPanelPlugin.java:419-420` uses `"$skills.points.universal_migrated_unallocated"` instead of `SpendService.POOL_UNALLOC`. The same file already uses the constant at `:1220`.
16. **Un-pend cascade treats `any` clauses as `all`.** `removePendingWithDependents` uses `n.getPrereqs()`, the flattened id list (`Node.java:52-54`). Removing one alternative of an `any` clause drops dependents that the other alternative still satisfies. No current tree JSON uses `"any"`, so this is latent; use `PrereqValidator.canPurchaseWithPending` per remaining node instead.

## Tests (missing or weak, ranked)

There are no tests under `test/skills_overhaul/` for anything in `ui/`. The purchase rules in the UI cannot be tested while they live in a GL panel class.

1. **Pending-set validation (B1, B2).** Extract a pure `PendingPurchasePlanner(TreeDef, snapshot, pending)` and test:
   - The tier gate still holds after un-pending the node that satisfied it.
   - A budget with `POOL_LOCK_KEY` set to another tree excludes the pool.
   - A dry-run of the whole set through `SpendService.spend` matches what the UI accepts.
2. **Respec gating (B3).** Test that `RespecRunner`/`RespecService` refuse a paid respec at 0 SP and allow the first free one.
3. **Un-pend cascade.** Cover `removePendingWithDependents` with chains, `any` clauses, and nodes justified only by the tier gate.
4. **Layout fit.** Test that `configureForViewport(List<TreeDef>, w, h)` produces `totalW <= w` and `totalH <= h` for the real trees, from the minimum supported resolution (1280×768 × 0.9/0.88 minus chrome) upward. This is pure maths on static fields and is easy to test.
5. **Active-slot click.** Test the displacement choice (A3) once it is moved out of the panel.

## Design notes

1. **Purchase rules are split across layers.**
   - Tier gate: UI only.
   - Budget: UI's own sum versus `SpendService`.
   - Prereqs: both.

   Make `level`/`tree` the single authority; the UI should only ask "can I add X to this pending set?" and render the answer.
2. **`PathTreeBuilder`'s layout metrics are mutable static fields** (`NODE`, `LANE_W`, …). `CharacterTabReplacer.install` (`:176-182`) calls `computeMetrics` against whatever values the previous panel left behind. Return a `Layout` value object from `configureForViewport` instead.
3. **There are two coordinate sources, reconciled every frame.** Geometry is computed (`nodeLocal`) and then overwritten from the engine's `PositionAPI` each frame (`syncNodeGeometryFromResolvedPositions`). Pick `PositionAPI` as the only source and drop the panel-local fallback hit test (`pickNodeAtPanelLocal`), which only adds a second, possibly inverted, Y convention (`eventToPanelLocalY`).
4. **`level` depends on `ui`.** `GameSpend` imports `skills_overhaul.ui.SkillUISounds`. Purchase feedback belongs in the caller, which also fixes advisory 14.
5. **With Second-in-Command enabled, the whole UI is off.** `isModEnabled("second_in_command")` makes the replacer defer for the entire session (`CharacterTabReplacer.java:125-138`), so those players have no in-game way to spend points. Document this, or offer a different entry point (an ability or a bar event).
