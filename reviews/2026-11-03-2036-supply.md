## Verdict

No blocking defect was verified in this area. The buffer arithmetic is correct for its tested cases, the listeners and the renderer are registered transiently once per load, and every current caller refunds the buffer correctly when the fleet cannot pay. The weaknesses are in the invariants. The cap is enforced only when scrap is added, so the buffer can sit well above it. Consuming from the buffer is not atomic, so each caller has to refund by hand. The HUD bar takes its x position from a world-space width. The three most valuable fixes:

1. **Clamp the buffer to the cap whenever the cap can drop (A1).** Clamp on read for spenders, or in a reconciler after `NodeApplyService` re-applies nodes and whenever cargo capacity changes. Today a Scrapheap respec, or selling freighters, leaves the buffer above the new cap. The surplus is then spendable, including on Letter of Marque's 50-scrap gate.
2. **Make `tryConsume` all-or-nothing (A3).** Pass the fleet's available supplies in, and return failure without touching memory. That removes six hand-written refund blocks in five callers.
3. **Position the HUD bar from `Global.getSettings().getScreenWidth()` (A2).** Do not use `viewport.getVisibleWidth()`, which is likely a world-space width that changes with campaign zoom.

## Advisory

### A1. The cap only limits filling; the buffer survives any drop in the cap

`src/skills_overhaul/supply/SupplyBufferService.java:62-66` (the `MemoryAPI` copy is at :122-126):

```java
        float cap = computeCap(mem, fleetCargoCapacity);
        float cur = SkillMemory.getSupplyBuffer(mem);
        float room = Math.max(0f, cap - cur);
        float take = Math.min(room, amount);
        SkillMemory.setSupplyBuffer(mem, cur + take);
```

The cap depends on cargo capacity (`FLEET_CARGO_RATIO`) and on `CAP_MULTIPLIERS` (Scrapheap ×1.5, `commander_corsair.json:86`). Both can fall. Nothing in the repo lowers the stored buffer when they do: the only writers are `add`, `tryConsume`, the caller refunds, and `LetterOfMarqueAbility.java:25`. The probe output, at commander level 2:

```
cap w/ scrapheap, cargo 300: 90.0
buffer after fill: 90.0
cap after respec, cargo 100: 40.0 buffer still: 90.0
add returns overflow: 5.0 buffer: 90.0
```

Scenario: fill the buffer while carrying extra freighters or while Scrapheap is owned, then sell the freighters or respec Scrapheap. The buffer stays at 90 against a cap of 40. `LetterOfMarqueAbility.java:18,24` then commissions a privateer at `(int) buffer` = 90 strength, which is impossible to reach legitimately at cap 40 (`MIN_SCRAP = 50`, `PrivateerFleetService.java:17`). Losing cargo ships in battle has the same effect without any intent to exploit. The renderer hides the overflow, because `SupplyBufferRenderer.java:48` clamps `fraction` to 1.

Fix: add `SupplyBufferService.clampToCap(mem, fleetCap)`. Call it from `ForgeCampaignBuffsTicker`, or from a once-a-day tick, and after `NodeApplyService` re-applies nodes. Alternatively, have the spenders read `min(buffer, cap)`.

### A2. HUD bar x position uses the viewport's visible width inside a UI-coordinate render pass

`src/skills_overhaul/supply/SupplyBufferRenderer.java:51`:

```java
        float x = viewport.getVisibleWidth() - barW - 20f;
```

`renderInUICoordsBelowUI` draws in screen/UI pixels. `ViewportAPI.getVisibleWidth()` is the viewport's visible width in world units, and it scales with the campaign zoom (view multiplier). If that holds, zooming out pushes the bar off the right edge and zooming in pulls it toward the centre. Every other screen-anchored element in the mod uses `Global.getSettings().getScreenWidth()` (`SkillTreeView.java:743`, `DialogHost.java:70`, `CharTabHost.java:147`). **Not verified in-game**: no game jar or runtime is available here. Fix: `float x = Global.getSettings().getScreenWidth() - barW - 20f;`.

### A3. `tryConsume(ABILITY)` drains the buffer before the caller knows the fleet can pay; every caller hand-writes the refund

`src/skills_overhaul/supply/SupplyBufferService.java:79-86` (the `MemoryAPI` copy is at :134-141):

```java
        if (mode == DrainMode.ABILITY) {
            float cur = SkillMemory.getSupplyBuffer(mem);
            float take = Math.min(cur, remaining);
            r.fromBuffer = take;
            SkillMemory.setSupplyBuffer(mem, cur - take);
            remaining -= take;
        }
```

The rollback is copied in `ForgeService.java:52-55`, `CraftSuppliesAbility.java:32-35`, `CraftFuelAbility.java:32-35` and `UndergroundIntelAbility.java:38-42` and :49-53. `MobileFabUnitTicker.java:39-41` repeats it too, for UPKEEP mode, where `fromBuffer` is always 0 and the refund does nothing. All current copies are correct. A new caller that checks `fromFleet` and returns without the refund silently destroys buffer scrap. Fix: `tryConsume(mem, amount, mode, fleetAvailable)` should compute the split, return `null` (or `success=false`) when `fromFleet > fleetAvailable` without writing, and write only on success.

### A4. Dead API and stale docs in `SupplyBufferService`

- `DrainResult.shortfall` (`SupplyBufferService.java:37`) is never assigned anywhere in `src/`. The test asserts it is 0 (`SupplyBufferServiceTest.java:37,43`).
- `INCOME_BONUS_MULTIPLIER` and `applyIncomeBonus` (`:22`, `:90-92`) have no caller in `src/`. Only the test uses them.
- The `add` javadoc (`:57-58`) says "the caller routes overflow into normal fleet cargo". No caller does: `SalvageBonusListener.java:42` and `ScrapBeaconDevice.java:32-33` both drop the overflow.
- The `tryConsume` javadoc (`:72-73`) points to "SupplyBufferListener". That class was removed: `docs/audits/2026-07-07-full-audit.md:61` describes it, and it no longer exists.

Fix: delete the dead members and their test lines, and update the two javadocs.

### A5. Every operation exists twice, once for `Map` and once for `MemoryAPI`

`isUnlocked` (:41-47), `computeCap` (:50-54 vs :114-118), `add` (:60-68 vs :120-128) and `tryConsume` (:75-88 vs :130-143) have identical bodies. Only the `Map` copies are tested. The game runs only the `MemoryAPI` copies, apart from tests and `isUnlocked(Map)`. A fix applied to one copy (for example A1 or A3) can miss the other. `ZealDailyTicker.MemoryWrapMap` (`ZealDailyTicker.java:59`) already adapts `MemoryAPI` to `Map`. Fix: keep the `Map` implementations and have the `MemoryAPI` overloads delegate through that wrapper.

### A6. `ForgeCampaignBuffsTicker` scans all of global sector memory on every unpaused frame

`src/skills_overhaul/supply/ForgeCampaignBuffsTicker.java:77-87`:

```java
        List<String> keys = new ArrayList<String>(
                Global.getSector().getMemoryWithoutUpdate().getKeys());
        for (String key : keys) {
```

This copies every global memory key into a new list each frame, and calls `getEntityById` for each live device. The script is added unconditionally (`SkillsOverhaulModPlugin.java:112-113`), so it runs in every game, including games with no Artificer. Expiry has day granularity and the radius check needs no more than a few hertz. Fix: keep a single memory-held list of deployed device ids, and gate the loop with an `IntervalUtil` of about 0.25–1 s. Alternatively, do expiry once per `monotonicDay` change.

### A7. The buffer fill depends on listener order and counts loot the player never takes

`src/skills_overhaul/supply/SalvageBonusListener.java:35-42` mirrors 25% of `loot.getCommodityQuantity("supplies")` as soon as the loot is generated. The fill happens even if the player leaves those supplies behind on the loot screen. It also reads the loot before or after Corsair's `PostBattleSalvageMultiplierListener` inflates it (`PostBattleSalvageMultiplierListener.java:27-29`), depending only on registration order. Today `SalvageBonusListener` is added first (`SkillsOverhaulModPlugin.java:72` vs `:89-90`), so the buffer sees the pre-multiplier amount. Reordering those lines would silently change the balance. Fix: decide which amount should count and enforce it. Either compute the fill from the multiplier explicitly, or fold both into a single loot listener with a defined order. If only taken loot should count, document that the fill is on generation.

## Design notes

1. **Scrap Beacon plus Craft Supplies is a supply printer once forging is wired.** `ForgeRecipeRegistry.java:76-77` prices Scrap Beacon at 5 supplies with a 3-day cooldown. `ScrapBeaconDevice.java:14-24` adds 10 scrap every 2 days for 30 days, up to 150 before the cap. `CraftSuppliesAbility.java:15-17,40` turns 10 scrap into 10 real supplies every 2 days. Each 5-supply beacon can therefore return about 150 supplies. Today this is unreachable, because nothing calls `ForgeService.craft` (artificer review B3). Balance it before that wiring lands.
2. **`ForgeCampaignBuffsTicker` is in the wrong package.** It never touches the supply buffer, and all of its keys and writers are in `artificer/forge`. Move it there so the owning review sees it.
3. **The buffer has no owner object.** Its rules (cap, the unlock gate, ABILITY/UPKEEP order, refunds) are spread across static helpers and ten call sites. A small `SupplyBuffer` value class wrapping the memory key would keep the A1 and A3 invariants in one place.
4. **The day counter is copied three times.** `ForgeCampaignBuffsTicker.currentDay` depends on `AlphaStormAbility.monotonicDay` (`AlphaStormAbility.java:63`), and identical copies exist in `ZealDailyTicker.java:50` and `InfamyDailyTicker.java:27`. The comment at `ForgeCampaignBuffsTicker.java:126` ("Must match the writers") depends on those copies staying the same. Use one shared utility instead.
5. **Nav Beacon and Sensor Beacon stack.** Both add +50% sensor range under different modifier ids (`ForgeCampaignBuffsTicker.java:47` and `:105`), giving +100% together. If they should not stack, share one id or take the maximum.
