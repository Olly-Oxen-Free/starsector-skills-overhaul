# Deep review: `src/skills_overhaul/effect/` (2026-11-01-2306)

Scope: all 87 files under `src/skills_overhaul/effect/` (3,134 lines): `EffectHandler`, `EffectRegistry`, `NodeEffectApplier`, `SkillsOverhaulCombatPlugin`, and every handler/listener under `effect/handlers/**`. Also read: `data/config/skills_overhaul/trees/*.json` (every `effects` entry), `data/config/settings.json`, and the code on the other side of the area's boundary: `level/GameSpend.java`, `level/RespecRunner.java`, `state/NodeApplyService.java`, `basics/ActiveLaneService.java`, `SkillsOverhaulModPlugin.java`, `console/OrphanSkillGranter.java`, `ui/CharacterTabPanelPlugin.java:1170-1197`, and the parts of `pilot/defense/DefenseCombatPlugin.java`, `pilot/gunnery/GunneryCombatPlugin.java` and `commandant/FieldCommandsService.java` that consume `ACTIVE_NODES`.

Build: **not compiled.** `build.sh` hardcodes `GAME_DIR="/home/jayden-eppcohen/Games/Starsector"`, and the Starsector API jars are not in this container. Starsector API behaviour cited below comes from reading the code, not from running it.

## Verdict

The handler layer assumes that a handler's `apply()` runs somewhere it can change the thing it targets. For campaign memory flags that holds. For per-ship combat stats it does not: purchase and load both happen in the campaign, where `getCombatEngine().getPlayerShip()` is null. As a result, six purchasable pilot nodes never apply some or all of their stats. The three most valuable fixes:

1. **Apply the stat parts of those six handlers in combat** (B1). Route them through `SkillsOverhaulCombatPlugin.applyShipStatEffect` the same way `SO_piloted_stat` is routed. Today Glass Cannon, Redundant Bays, Defensive Configuration, Derelict Fortifications, the absorption/arc part of Fortress Shield, and the upkeep part of Shield Mastery do nothing.
2. **Remove a node's effects before taking it out of the active-basics list on respec** (B2). With the current order, the T0 `core` channel is never removed, and Artificer's forge recipes stay unlocked after a respec.
3. **Reset every static that a handler writes** (B3). `BountyBoardListener.active`, `FieldCommandsService.active` and the salvage multipliers carry over from one save to the next within a session.

## Blocking

### B1. Six pilot nodes' combat stats are never applied

Files:
- `src/skills_overhaul/effect/handlers/gunnery/SOGunneryGlassCannonHandler.java:15`
- `src/skills_overhaul/effect/handlers/defense/SODefenseRedundantBaysHandler.java:14`
- `src/skills_overhaul/effect/handlers/defense/SODefenseConfigHandler.java:15`
- `src/skills_overhaul/effect/handlers/defense/SODefenseDerelictFortHandler.java:16`
- `src/skills_overhaul/effect/handlers/defense/SODefenseFortressShieldHandler.java:15`
- `src/skills_overhaul/effect/handlers/defense/SODefenseShieldMasteryHandler.java:14`

Each of these handlers contains:

```java
        ShipAPI ship = getPlayerShip();
        if (ship == null) return;
```

`getPlayerShip()` returns `Global.getCombatEngine().getPlayerShip()`. Handlers run in only two places, `GameSpend.purchase` and `NodeApplyService.reapplyAllOwned` (on load), and both run in the campaign, so `ship` is always null and the stat block never runs. The only per-combat path, `SkillsOverhaulCombatPlugin.applyShipStatEffect`, handles nothing except `SO_piloted_stat`:

```java
        if (type.equals("SO_piloted_stat")) {
```
(`src/skills_overhaul/effect/SkillsOverhaulCombatPlugin.java:74`)

Nothing else applies these stats either. `DefenseCombatPlugin` only implements the breach mechanic (Fortress Shield) and the hard-to-soft flux conversion (Shield Mastery). `GunneryCombatPlugin:120` applies only the Killing Machine "relief" against a Glass Cannon penalty that never existed. Nothing in `src/` checks for `so_defense_redundant_bays`, `so_defense_config` or `so_defense_derelict_fort`.

Failure scenario: the player buys Glass Cannon (`pilot_gunnery.json:86`) and gets neither the +30% damage nor the +20% hull damage taken (`SOGunneryGlassCannonHandler.java:17-19`). With Killing Machine, the "relief" multiplier then *reduces* hull damage below baseline, so the node is a pure buff. Redundant Bays, Defensive Configuration and Derelict Fortifications have no effect at all. Fortress Shield loses its 0.90 absorption and +20 arc, and Shield Mastery loses its 0.75 upkeep.

Fix: give each handler an `applyTo(MutableShipStatsAPI, ShipAPI, nodeId, fx)` (the ship is needed for the `shield_shunt` and d-mod checks). Dispatch to it from `SkillsOverhaulCombatPlugin.applyShipStatEffect` by `type`, and reduce the handlers' `apply()` to the `ACTIVE_NODES.add` marker.

### B2. Respec never removes T0 `core`-channel effects

File: `src/skills_overhaul/level/RespecRunner.java:71-77`

```java
        // Drop T0 nodes from active basics
        for (Node n : ownedBefore) {
            if (n.getY() == 0) ActiveLaneService.onUnpurchased(mem, n.getId());
        }

        // Remove effects
        for (Node n : ownedBefore) NodeEffectApplier.remove(n);
```

`NodeEffectApplier.remove` gates on the active set **after** the node has already been dropped from it:

```java
        boolean t0Active = isT0 && ActiveLaneService.isActive(mem, n.getId());
```
(`src/skills_overhaul/effect/NodeEffectApplier.java:24`), then `if ("core".equals(channel)) return t0Active;` (line 64).

Failure scenario: the player owns `artificer_t0` with it active and respecs the commander tree. The `core` channel's `remove()` is skipped, so `ForgeRecipeRegistry.lock("drone_wakes")` and `lock("sensor_beacon")` never run. Both recipes stay forgeable for the rest of the session with the tree refunded. `$skills.{artificer,commandant,zealot,corsair}.t0.coreActive` also stay set in the save permanently, because `reapplyAllOwned` only applies and never clears.

Fix: run `NodeEffectApplier.remove(n)` before `onUnpurchased`. Separately, consider making `remove()` ungated (see A1).

### B3. Handler-owned statics leak across save loads

File: `src/skills_overhaul/state/NodeApplyService.java:63-78`. `resetTransientStatics()` clears the `ACTIVE_NODES` sets and five registries but not these three:

- `BountyBoardListener.active` / `weaponDropMult` (`effect/handlers/corsair/BountyBoardListener.java:13-14`)
- `FieldCommandsService.active` (`commandant/FieldCommandsService.java:15`; set by `SOFieldCommandsHandler.java:11`, read at `FieldCommandsService.java:59`)
- `PostBattleSalvageMultiplierListener.MULTIPLIERS` (`effect/handlers/corsair/PostBattleSalvageMultiplierListener.java:13`)

Failure scenario: in one session, the player loads save A, which owns `corsair_t2_bounty_board` and two `corsair_salvage_mult` nodes, then loads save B, which owns neither. In B, each won engagement still pays out:

```java
            Global.getSector().getPlayerFleet().getCargo().getCredits().add(kills * 800f);
```
(`BountyBoardListener.java:29`), loot is still multiplied by A's 1.2 × 1.3, and Field Commands still runs if A had it.

Fix: add `BountyBoardListener.active = false; weaponDropMult = 1f;`, `FieldCommandsService.active = false;` and a `PostBattleSalvageMultiplierListener.clear()` to `resetTransientStatics()`.

### B4. `corsair_t0` applies its −10% sensor profile twice

Data: `data/config/skills_overhaul/trees/commander_corsair.json:7-9`

```json
        { "type": "corsair_t0", "channel": "base" },
        { "type": "corsair_stat_bonus", "channel": "base", "scope": "fleet",
          "stats": [ { "key": "sensorProfileMod", "value": -0.10 } ] },
```

`CorsairT0Handler.java:18-19` already applies the reduction under its own modifier id:

```java
            Global.getSector().getPlayerFleet().getStats().getDetectedRangeMod()

```

`StatBonusHandler.java:79` then applies it again under a different id (`nodeId`):

Failure scenario: buying Corsair T0 gives 0.9 × 0.9 = 0.81, a −19% detected range instead of −10%.

### B5. D-mod counting never matches vanilla d-mods, so Scrapheap and Scrappy Maintenance do nothing

```java
            if (h.endsWith("_dmod") || h.contains("_d_") || h.contains("_d ")) c++;
```

and `src/skills_overhaul/effect/handlers/corsair/CorsairCombatPlugin.java:257`


Vanilla d-mod ids (`degraded_engines`, `faulty_grid`, `compromised_structure`, `glitched_sensors`, and so on) match none of these patterns. The same package already counts correctly by tag, at `defense/SODefenseDerelictFortHandler.java:53`:

## Advisory (ranked)

1. **`remove()` is gated by the *current* oath and active-basics state, not the state at apply time** (`NodeEffectApplier.java:25-27`, `54-71`). An effect applied under oath X or `requiresActiveBasic` will not be removed after the oath or active set changes. No tree data uses `oath` or `requiresActiveBasic` today, so this is latent, but it is the same class of bug as B2. Make `remove()` unconditional; handler removes are idempotent.
2. **Console orphan grants die on every load.** `SkillsOverhaulModPlugin.java:103-104` runs `OrphanSkillGranter.applyAllOnLoad()` *before* `NodeApplyService.reapplyAllOwned()`, whose `resetTransientStatics()` clears `DefenseCombatPlugin.ACTIVE_NODES`. The `impact_mitigation` orphan is an `SO_piloted_stat` effect whose node is in no tree, so `SkillsOverhaulCombatPlugin` never sees it. Its `damageReduction` would also map to hull-only DR (`SOPilotedStatHandler.java:72`), and its `hitChance` is logged and dropped. Swap the call order and give orphans a combat path.
3. **Modifier-id collision in `so_maneuver_engine_tuning`** (`pilot_maneuvering.json:37`: `"accelDecelBonus": 0.25, "maneuverBonus": 0.10`). Both keys call `s.getTurnAcceleration().modifyPercent(id, …)` with the same `id` (`SOPilotedStatHandler.java:109` and `113`), so whichever key `JSONObject.keys()` yields last wins (+25% or +10%; HashMap order, not specified). Suffix the id per key.
4. **Per-fleet-member campaign mods only reach ships present at apply time**: `SOFieldLogisticsHandler.java:19-23`, `SOMobileArsenalHandler.java:19-22`, `SONavMatrixHandler.java:18-25`, `DModDpScalingHandler.java:30-35`, `StatBonusHandler.java:47-49`. Ships bought or recovered later lack the bonus until the next load. Ships that leave the fleet keep the modifier, because `remove()` only walks current members.
5. **`PostBattleRestoreListener` ignores max CR and stacks per engagement round.** `m.getRepairTracker().setCR(Math.min(1f, currentCR + crRestore));` (`PostBattleRestoreListener.java:59`) clamps to 100%, not to the member's max CR. `reportPlayerEngagement` fires per engagement (for example, battle then pursuit), so hull and CR restore apply twice. Both `catch (Throwable t)` blocks swallow failures silently (lines 52, 60).
6. **Memory flags set with `expire = 0f`**: `$so_collective.active` (`collective/SOCollectiveT0Handler.java:13`, read by `collective/CollectiveBattleEndListener.java:23`), `$so_collective.terrain_immune` (`collective/SOMagneticShieldingHandler.java:12`), and the four `T3_FLAG`s (`SOCombatScriptHandler.java:17`, `SOArtificerCombatScriptHandler.java:17`, `SOZealCombatScriptHandler.java:17`, `corsair/CombatScriptHandler.java:23`). If MemoryAPI treats 0 as "expire at next advance" (unverified here: no API jar), Collective's battle-end processing is gated off within a frame of each load or purchase. Use the two-arg `set(key, value)` for persistent flags. The other handlers in this package already do.
7. **Loot inflation calls `addCommodity` on every stack** (`PostBattleSalvageMultiplierListener.java:27-29`), including weapon, fighter-wing and special-item stacks, where `getCommodityId()` does not name a commodity. Filter with `st.isCommodityStack()`.
8. **Pilot stats follow the first player ship only** (`SkillsOverhaulCombatPlugin.java:42-48`). After a mid-battle transfer of command, the new ship has no pilot stats and the old one keeps them.
9. **`CorsairT0Handler` dereferences `getPlayerFleet()` without a null check** (`corsair/CorsairT0Handler.java:18`, `31`). Every sibling handler guards for this.
10. **Semantic mismatches in `SOPilotedStatHandler`**: `fireChanceReduction` modifies `getEngineMalfunctionChance`/`getWeaponMalfunctionChance` (CR malfunctions, not fire; lines 62-65). `projectileFragResist` is applied as fragmentation damage taken (line 74). Eighteen param keys are logged and skipped as "no direct API" (lines 142-153), including `weaponHPBonus`, `massMult`, `crRegenInCombat`, `ecmRatingBonus` and the three `air_superiority` keys, so nodes such as `so_systems_air_superiority` and `so_defense_immovable_object` are largely inert.
11. **Dead or ignored data and code**:
    - `BountyBoardListener.weaponDropMult` is written, never read.
    - `RaidZealListener.onRaid` has no caller.
    - `corsair_dmod_dp`'s `dpPerDMod`/`crPenaltyMod` are ignored (`commander_corsair.json:39`, `57`), so two of its three uses are no-ops.
    - `SOFleetStatHandler` drops `suppliesUseMod`.
    - The `coreActive` and `tier_reached.3` keys have no readers.
    - `SOSystemsEMPSpecialistHandler` fetches a ship and does nothing with it.
    - `SOSystemsExperimentalOverridesHandler.remove` sets `false` where every sibling uses `unset`.
12. **Duplication**: ten private copies of `getPlayerShip()`; four near-identical `*CombatScriptHandler` classes that differ only in target set and flag prefix; and `SOPilotedStatHandler`'s parallel `applyKey`/`unapply` switches, which can drift (a key added to one is silently missing from the other).

## Design notes

1. `EffectHandler` mixes three lifetimes behind one `apply/remove` pair: persistent campaign state (memory keys, fleet stats), JVM statics (`ACTIVE_NODES`, registries), and per-combat ship stats. Splitting it into `CampaignEffect` and `CombatEffect.applyTo(ShipAPI)` would make B1 impossible to write and remove the null-ship branches.
2. The truth for "what is owned and active" is the `$skills.purchased.*` memory keys, yet each combat plugin reads its own static mirror. Combat plugins could compute the active set from memory in `init()`, which would remove both the load-time re-seeding and the cross-save leak class (B3).
3. Static `boolean active` flags (`BountyBoardListener`, `FieldCommandsService`) are single-owner. If a second node ever uses the same effect type, removing one disables both. A keyed set, like `CommandFieldService`'s params, scales better.
4. Magic numbers are split between data and code: `SOFieldLogisticsHandler`, `SOMobileArsenalHandler`, `SOForcedMarchHandler`, `SORefittingHandler` and the T0 handlers hardcode values the tree JSON could carry, which is how B4 happened.
5. `SOPilotedStatHandler`'s `apply()`/`remove()` are documented no-ops, so the purchase-time and combat-time paths look symmetric but are not. Make the asymmetry explicit by having those methods do nothing.
