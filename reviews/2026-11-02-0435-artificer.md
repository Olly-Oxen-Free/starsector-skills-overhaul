Scope: every file under `src/skills_overhaul/artificer/` (62 files, 2,777 lines: root services, `forge/`, `forge/devices/`, `alphastorm/`), its data (`data/config/skills_overhaul/trees/commander_artificer.json`, `data/campaign/abilities.csv` rows 8-9, `data/campaign/special_items.csv` row 2, `data/config/settings.json` plugin rows 10-12), and the code outside the package that calls into it: `SkillsOverhaulModPlugin`, `state/NodeApplyService`, `effect/EffectRegistry`, the `SO*` artificer handlers in `effect/handlers/`, `support/InvincibilityListener`, `supply/SupplyBufferService` and `supply/ForgeCampaignBuffsTicker`. Base: `master` @ b3f796f. Before this run the only reviews were `effect` and `ui`, both on unmerged review branches. `artificer` had never been reviewed and was the largest unreviewed area.

Build: **not run.** `build.sh` hard-codes `GAME_DIR=/home/jayden-eppcohen/Games/Starsector`, and the Starsector API jars it links against are not in this container. That rules out `./build.sh` and `./build.sh test`, because the tests compile against `src`. Every finding below comes from reading the source. ## Verdict

Three things need fixing first. (1) **Replace the `cycle*365 + getDay()` "monotonic day" with a real elapsed-day clock.** `getDay()` is the day of the month, so this value goes back down at every month boundary. The result: Alpha Storm becomes a free MILD storm after its first month boundary, then charges hundreds of days at once when the cycle rolls over. Mobile Fab upkeep stops being billed. Officer Imprint, Nav Beacon, Slipstream Seeder and Hypercloud stay active until the end of the cycle. (2) **Fix the ×100 unit error in `PhaseSharedBonusService.computeBonus`.** Any real deployment currently gets the 150% cap, so Technological Transcendence gives phase ships 2.5× energy damage and 2.5× flux dissipation. (3) **Wire the forge loop end-to-end.** On `master` nothing calls `ForgeService.craft` or `ForgeBattleHook.offerDeployBattleDevice`, and neither ability is ever granted. So the 19 recipes, the free-deploy quota and the Alpha Storm capstone (cost 3) can be bought but never used.

## Blocking

### B1. The "monotonic day" counter resets every month: wrong billing, effects that never end, a supply wipe at cycle rollover

The same formula is copied into eight places in this area, and one more outside it:

- `src/skills_overhaul/artificer/alphastorm/AlphaStormAbility.java:59-62`
  ```java
  public static int monotonicDay() {
      return (int) Global.getSector().getClock().getCycle() * 365
              + (int) Global.getSector().getClock().getDay();
  }
  ```
- `src/skills_overhaul/artificer/forge/MobileFabUnitTicker.java:51-54` (same body)
- `src/skills_overhaul/artificer/ArtificerCombatPlugin.java:117-118`: `int today = (int) (Global.getSector().getClock().getCycle() * 365 + Global.getSector().getClock().getDay());`
- `src/skills_overhaul/artificer/forge/devices/OfficerImprintDevice.java:18-19`: `... getCycle() * 365 + (int) Global.getSector().getClock().getDay() + 7;`
- `src/skills_overhaul/artificer/forge/devices/NavBeaconGeneratorDevice.java:10`: `int expire = currentDay() + 30;`
- `src/skills_overhaul/artificer/forge/devices/SlipstreamSeederDevice.java:11`: `int expire = currentDay() + 45;`
- `src/skills_overhaul/artificer/forge/devices/HypercloudGeneratorDevice.java:10`: `int expire = currentDay() + 60;`
- `src/skills_overhaul/artificer/forge/devices/SensorBeaconDevice.java:21-22`, `CommJammerDevice.java:21-22` (`+ 7`, `+ 30`)
- Outside this area, the consumer: `src/skills_overhaul/supply/ForgeCampaignBuffsTicker.java:125-127`

`CampaignClockAPI.getDay()` returns the day of the month, not the day of the year, so this value falls at every month boundary. *(This is the documented API meaning. It could not be checked against the jar here.)* Failure scenarios:

1. **Alpha Storm (`AlphaStormCampaignTicker.java:40-43`)**
   ```java
   } else if (today > last) {
       ...
       for (int day = last + 1; day <= today; day++) {
   ```
   The storm starts on day 28 of a month (`start = C+28`). On day 1 of the next month `today = C+1`. That is not greater than `last`, so billing stops for the rest of the cycle. At the same time `AlphaStormState.intensity` computes `d = today - start`, which is negative, so `d <= 2` and the storm stays MILD. The fleet keeps the storm's ×0.90 detected-range modifier and its burn bonus for free. When the cycle rolls over, `today` jumps by about 335, and the loop bills each skipped day at its "own" intensity, which is SEVERE (10 supplies/day). It does this in a single frame. With 2,000 supplies in cargo, the player loses up to ~2,000 supplies at once, and then the storm switches off.
2. **Mobile Fab upkeep (`MobileFabUnitTicker.java:30`)**: `if (today <= last) return;`. Once `last` holds day 30 or 31 of any month, every later day in that cycle compares as `<= last`. The 1-supply/day upkeep is skipped for up to 11 months, and `K_FAB_INACTIVE` is never set.
3. **Officer Imprint**: deployed on day 28, `expire = C+35`. Day-of-month never reaches 35, so `today < exp` at `ArtificerCombatPlugin.java:119` stays true for the rest of the cycle. That means up to +20% fighter damage and speed for about a year instead of 7 days. Deployed on day 1, `expire = C+8`, and the buff comes back on days 1-7 of every later month.
4. **Nav Beacon / Slipstream / Hypercloud**: `+30/+45/+60` always exceeds the largest possible day of the month, so `ForgeCampaignBuffsTicker.isActive` keeps +2 burn, +50% sensor range and −50% fuel use running until the cycle ends.

**Fix:** store `clock.getTimestamp()` at start, deploy or bill time, and measure with `clock.getElapsedDaysSince(ts)`. Floor the result to whole days for billing. Put this in one shared helper, for example `skills_overhaul.state.GameDays`, and use it from all ten call sites. Cap the Alpha Storm catch-up loop the way Mobile Fab caps its loop (`Math.min(7, ...)`).

### B2. Technological Transcendence always gives +150%: unit error in the pool formula

`src/skills_overhaul/artificer/PhaseSharedBonusService.java:11` and `:19-21`
```java
float raw = POOL_SIZE / (totalPhaseDPDeployed / 10f);
...
if (raw < FLOOR_BONUS) return FLOOR_BONUS;
if (raw > CAP_BONUS) return CAP_BONUS;
```
`raw` comes out in percentage points: 150 / shares. `FLOOR_BONUS` and `CAP_BONUS` are fractions (0.20 and 1.50). So `raw = 1500 / totalDP`, and it falls below the cap only when more than **1,000 DP** of phase ships are deployed at once. No real battle has that. The test documents the intended behaviour at `test/skills_overhaul/artificer/PhaseSharedBonusServiceTest.java:22`: "1 phase ship at 50 DP → 5 shares → 30% per share". The code gives 150%. `ArtificerCombatPlugin.java:302-303` applies `modifyMult(..., 1f + bonus)` to both energy weapon damage and flux dissipation on every phase ship.

Failure scenario: two Harbingers and a Doom (about 85 DP) get ×2.5 energy damage and ×2.5 dissipation. The intended values are ×1.18 each, and the floor is ×1.20. This is a balance exploit on a 2-point T4 node.

**Fix:** `float raw = (POOL_SIZE / (totalPhaseDPDeployed / 10f)) / 100f;`. Rewrite the test assertions to match the spec examples (50 DP → 0.30, 150 DP → 0.20 floor, 10 DP → 1.50 cap). Delete the stream-of-consciousness comment at lines 12-18.

### B3. The forge and Alpha Storm can be bought but never used on `master`

- `src/skills_overhaul/artificer/forge/ForgeService.java:38`: `public static boolean craft(String recipeId) {`. This is the only way to create a `forge_device` item, and nothing in `src/` calls it.
- `src/skills_overhaul/artificer/forge/ForgeBattleHook.java:24`: `public static void offerDeployBattleDevice(String recipeId) {`. This is the only producer of `DEPLOY_ORDER_KEY`, and nothing calls it. `ForgeBattlePlugin` therefore always drains an empty queue.
- `src/skills_overhaul/effect/handlers/SOArtificerT0Handler.java:22-26` and `SOArtificerT5Handler.java:12-15` set memory flags only. No file in `src/` calls `addAbility`, so `skills_overhaul_deploy_forge_device` and `skills_overhaul_alpha_storm` (`data/campaign/abilities.csv:8-9`) never appear on the player's ability bar.

Failure scenario: the player spends 1 + 15 + 8 + 3 points down the Artificer tree. Every `SO_forge_recipe_unlock`, `SO_forge_quota_bonus` and the T5 capstone does nothing they can see. The only effects that work are the combat stat modifiers and the automated-points bonus.

`feature/skills-panel-restructure` adds `AbilityGrants.grant(...)` to both handlers. That branch still has no caller for `craft` or `offerDeployBattleDevice`, so merging it alone gives the player an ability that is always unusable (`DeployForgeDeviceAbility.isUsable` returns false with nothing held).

**Fix:** add a crafting entry point (an ability, an interaction dialog option, or a panel button) that calls `ForgeService.craft`. Add a pre-battle hook, for example in `ForgeBattleHook.reportPlayerEngagement` or in the deploy dialog, that calls `offerDeployBattleDevice`. Land the ability grants.

## Advisory

Ranked by risk.

1. **The special item icon points at another mod's graphics.** `data/campaign/special_items.csv:2` uses `graphics/icons/cargo/IndEvo_consumable_missile_pulse.png`. That file is not in this repo, and Industrial Evolution is not in `mod_info.json` `dependencies`. On an install without IndEvo, the icon is missing at best. If Starsector treats a missing spec sprite as a fatal load error, the game crashes at startup *(engine behaviour, unverified)*. Ship an icon in `graphics/`.
2. **Eight of the twelve over-quota penalties do nothing.** `AlphaStormEmitterPenalty`, `DerelictDroneSpawnerPenalty`, `DisruptorRelayPenalty`, `DroneWakesPenalty`, `GravitonAnchorPenalty`, `MagneticFieldEmitterPenalty`, `PulsarArrayPenalty` and `RepairPodPenalty` each only write a flag, for example `DroneWakesPenalty`: `"$skills.artificer.forge.drone_wakes_fragile", true`. No code anywhere in `src/` reads those flags. The flags are also never unset, so they pile up in the save. Deploys over the quota are effectively free once B3 is fixed. Either have each device read its flag, or pass `overQuota` into the device, which already receives it in `deployBattle(engine, overQuota)` and ignores it in every implementation.
3. **The battle plugins don't skip the simulator or missions.** `ForgeBattlePlugin.java:30-34` and `AlphaStormBattleScript.java:23-26` check only `engine.isPaused()`, then call `Global.getSector().getMemoryWithoutUpdate()`. In the refit simulator, the queued battle devices are drained and fired, so the real battle loses them, and the Alpha Storm penalties hit sim ships. In title-screen missions, `Global.getSector()` may be null, which would be an NPE every frame *(engine behaviour, unverified)*. Add `if (engine.isSimulation() || Global.getSector() == null) return;` (or check `engine.isInCampaign()`).
4. **Final Gambit may not actually destroy the ship.** `FinalGambitService.java:79`: `s.setHitpoints(0f);`. Setting hitpoints does not go through the engine's destruction path, so the ship can linger at 0 HP without exploding *(engine behaviour, unverified)*. Kill it with `engine.applyDamage(s, s.getLocation(), s.getMaxHitpoints()*10, DamageType.HIGH_EXPLOSIVE, 0, true, false, s)`. Also, `triggered` (line 25) is a static `Set<ShipAPI>` that keeps the last battle's ships alive until the next battle starts.
5. **The beam contact timer may never reach its threshold.** `ArtificerCombatPlugin.java:75`: `if (tgt == null || !beam.didDamageThisFrame()) continue;`. Lines 87-89 reset the timer whenever a source misses a target for one frame. If beams deal damage in intervals rather than every frame, contact resets constantly and the 3-second threshold is never reached. Even if they don't, the timer only adds `amount` on frames that dealt damage. Track "beam is touching the target" (`beam.getDamageTarget() != null` with the beam firing), and allow a short grace period before resetting.
6. **Alpha Storm's +1 quota is lost on reload.** `AlphaStormAbility.java:30` registers `FreeDeployQuotaTracker.registerBonus(QUOTA_BONUS_KEY, 1)`, and that state lives only in a static. `NodeApplyService.java:76` (`FreeDeployQuotaTracker.reset()`) clears it on every load, while `AlphaStormState.K_ACTIVE` stays in sector memory. Re-register it in `reapplyAllOwned` when `AlphaStormState.isActive(mem)`. Separately, confirm the design: T5 already grants `{"key":"alpha_storm","value":1}`, and activating the ability adds a second +1.
7. **Tachyon Forge base effects are never applied.** `SOArtificerT0Handler.java:18-21` sets `$skills.artificer.t0.supply_reduction` (0.20) and `$skills.artificer.t0.sensor_range_bonus` (0.30). Nothing reads either key. So T0's "base" channel only sets the purchased flag, which gates Mobile Fab upkeep. The player pays upkeep and gets nothing for it.
8. **Spawned drones, mines and entities probably fail silently, and the device is still used up.** `DerelictDroneSpawnerDevice.java:15` (`"tesseract_small";  // verify vanilla automated drone`), `DroneWakesDevice.java:26` (`"mining_drone" : "borer_drone"`) and `SelfReplicatingMinefieldDevice.java:20` (`"mine_strike_drone"`) pass these ids to `createFleetMember(FleetMemberType.SHIP, id)`, which expects a **variant** id. `CommJammerDevice.java:18` uses custom entity type `"jammer_station"`. When any of these ids doesn't exist, the exception is caught, logged as a warning, and the item is gone. Check them against the vanilla `.variant` files and `custom_entities.json`.
9. **Two recipe descriptions don't match what the device does.** `ForgeRecipeRegistry.java:69` says "Reduces burn cost in radius", but `ForgeCampaignBuffsTicker.java:46-47` gives +50% sensor range everywhere. `ForgeRecipeRegistry.java:93` says "Hyperspace cloud reduces sensor profile", but the ticker applies −50% fuel use (`:54-55`).
10. **Forge cooldown units are probably wrong.** `ForgeService.java:62`: `long cdEnd = now + r.cooldownDays * 86_400_000L;`. This assumes `getTimestamp()` counts real milliseconds. Use `clock.getElapsedDaysSince(start) >= cooldownDays` instead, which is the same fix as B1.
11. **The Scrap Beacon interval runs in seconds, not days, and is lost on save.** `ScrapBeaconDevice.java:14`: `new IntervalUtil(2f, 2f);  // 2 in-game days`. `EveryFrameScript.advance(amount)` gets seconds, so the 150-supply total pays out in about 30 real seconds instead of 30 days. The script is also added with `addTransientScript`, so a save/load loses whatever income is left.
12. **ECM Wave.** `ECMWaveDevice.java:15` declares `DISABLE_DURATION = 5f`, but nothing uses it. Line 23 calls `w.disable()` on every enemy weapon with no timed re-enable. On the player side, the ECM node (`ArtificerCombatPlugin.java:169-175`) turns `enemyWeaponRangePenaltyMult` into a *player* range bonus. The name and the effect disagree, so confirm which one the spec intends.
13. **Limit Breaker's armor bonus probably has no effect.** `ArtificerCombatPlugin.java:324`: `s.getMutableStats().getArmorBonus().modifyMult("artificer_t4_limit_breaker", 1.20f);`. It is applied every frame after the ship spawns, but the armor grid is set up at spawn, so a later armor-rating change does not refill the grid *(engine behaviour, unverified)*. Apply it pre-combat through a hullmod or `applyEffectsBeforeShipCreation`.
14. **`AutomatedShipCapApplier`.** It stamps `$autoPointsMult` only on purchase and load (lines 52-71). Automated ships recovered later, or ships whose AI-core captain is swapped, don't get the multiplier. `mem.unset` at line 68 would also wipe any multiplier that vanilla or another mod set. `countPlayerAutomatedPoints` and `overCapForPlayerFleet` (lines 77-92) have no callers.
15. **Performance: O(n²) work per frame.** `ECM.apply` (`ArtificerCombatPlugin.java:169-171`) calls `getPlayerECMRatingLive()` and `getEnemyECMRatingLive()`. Each of those walks every ship, and `ECM.apply` itself runs once per friendly ship. That includes fighters, because the loop at lines 50-53 doesn't filter them. `PowerGrid.apply` (lines 287-291) does the same thing with a nearest-enemy scan. Compute both once per frame in `advance` and pass the results in.
16. **`ForgeDeviceItemPlugin` is a bare `SpecialItemPlugin`.** `getSpec()` returns `null` (lines 108-110) and `render` does nothing (lines 91-94). Any vanilla code that calls `getSpec()` on a cargo stack can throw an NPE, and the item has no icon. Extend `BaseSpecialItemPlugin` instead.
17. **Dead code.** In `MobileFabUnitTicker.java:39-41`, the buffer refund runs in `UPKEEP` mode, where `SupplyBufferService` never touches the buffer, so `dr.fromBuffer` is always 0. The `$skills.artificer.{final_gambit,transcendence,carrier_command,t5}.purchased` flags are written and never read.

## Tests

Ranked by value.

1. **Day arithmetic (B1).** There is no test for how a day is computed across month or cycle boundaries. Once the shared helper exists, test the billing and intensity loop with a 31→1 month boundary and a cycle rollover.
2. **`AlphaStormBillingTest` doesn't test the ticker.** It copies the billing loop into the test (lines 22-25) instead of running `AlphaStormCampaignTicker`, so the real loop and its missing cap are never exercised. Move the loop into a pure static method that both the ticker and the test call.
3. **`PhaseSharedBonusServiceTest` asserts the bug.** Lines 7-10 expect 1.50 for 50-150 DP. Replace them with the spec examples from B2.
4. **No test checks that the forge loop is reachable.** Nothing covers craft → hold → deploy → `ForgeBattlePlugin` drain. A test that `ForgeBattleHook.recordDeploy` is called from a real path would have caught B3.
5. **Penalties:** no test checks that a device behaves differently when `overQuota` is true (Advisory 2).
6. **Reload state:** no test checks that `reapplyAllOwned` restores the Alpha Storm quota bonus and `ACTIVE_NODES` after `reset()` (Advisory 6).
7. **`ForgeServiceTest` (19 lines)** covers only `cooldownActive`. Nothing tests the supply refund path when the fleet runs short.

## Design notes

1. Create one time abstraction (`GameDays.now()` / `elapsedSince(ts)`) and ban hand-rolled `cycle*365+day` with a grep check in `build.sh test`. The same mistake appears in at least three packages.
2. Battle devices hard-code `(0,0)` as the field centre (`RepairPodDevice`, `GravitonAnchorDevice`, `MagneticFieldEmitterDevice`, `AlphaStormEmitterDevice`). Anchor them to the player's deployment point or the flagship so the effect lands where the fight is.
3. Combat effects reapply `modifyMult` to every ship every frame and almost never `unmodify`. Removing a node mid-campaign is safe only because combat stats are rebuilt per battle. Stat changes that should stay fixed for a battle belong in `applyEffectsBeforeShipCreation` (hullmod or skill), not in an every-frame plugin.
4. Effect state is split between JVM statics (`ACTIVE_NODES`, `BONUSES`, `UNLOCKED`) and sector memory. Each new static needs a matching line in `NodeApplyService.reapplyAllOwned`, which is easy to forget (Advisory 6). Derive the statics from owned nodes in one place.
5. The `try { ... } catch (Throwable t) {}` blocks around stat calls (for example `ArtificerCombatPlugin.java:181-183`, `190-192`) hide API mismatches that should fail loudly while the mod is being developed. Log them at least once.
