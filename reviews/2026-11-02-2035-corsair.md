Build: **not compiled.** `build.sh` points at `/home/jayden-eppcohen/Games/Starsector`, and no `starfarer.api.jar` exists anywhere in this container. Every claim below about Starsector API behaviour comes from reading the code, not from running it.

## Verdict

The pure logic is sound: the Infamy ring buffer, strength bands, payout cap and monotonic day counter are correct. The defects sit where the code meets the live game. The three most valuable fixes:

1. **Stale privateer faction relations.** The relations are written once per commission and only ever pushed towards hostile. A privateer commissioned after the player has made peace still treats that faction as an enemy (B1).
2. **Fallback marks spawn anywhere in the sector.** The Underground Intel fallback places its mark at any market of the chosen faction, anywhere in the sector. The player pays supplies for a mark the tooltip says is "within 10 LY", and `MarkIntel` drops it after 7 days when it is more than 30 LY away (B2).
3. **Privateer payout pays for kills the privateer did not make.** It is computed from every loss on the losing side, and stays capped per battle (A1).

## Blocking

### B1 — Privateer faction relations are never reset, so later commissions fight the player's current friends
`src/skills_overhaul/corsair/PrivateerFleetService.java:88-96`
```java
FactionAPI privFac = Global.getSector().getFaction("skills_overhaul_privateer");
if (privFac != null) {
    privateer.setFaction("skills_overhaul_privateer", true);
    privFac.setRelationship(Global.getSector().getPlayerFaction().getId(), 1.0f);
    for (FactionAPI f : Global.getSector().getAllFactions()) {
        if (f == Global.getSector().getPlayerFaction()) continue;
        if (f.isHostileTo(Global.getSector().getPlayerFaction())) {
            privFac.setRelationship(f.getId(), -1.0f);
        }
    }
}
```
`skills_overhaul_privateer` is one shared faction, and faction relationships are saved. The loop only ever writes `-1`, so a hostility is never undone.

Failure scenario:
1. The player is at war with Tri-Tachyon and commissions a privateer. `privFac` is set to -1 towards `tritachyon`.
2. The player makes peace. A month later they commission again. Tri-Tachyon is skipped (no longer hostile), but its -1 stays.
3. The new privateer is hostile to every Tri-Tachyon patrol, so it fights them in the player's systems. `PrivateerLifecycleScript.reportBattleFinished` then pays the player for those kills.

There is also the reverse case. A faction that turns hostile during the 30-day commission is never hostile to the privateer, but `PrivateerEscortAI.findHostileTarget` (`PrivateerEscortAI.java:101`, `if (!f.getFaction().isHostileTo(player.getFaction())) continue;`) still sends the escort to INTERCEPT that faction's fleets. The escort shadows them without fighting.

Fix: mirror the player faction exactly instead of only writing hostiles. Put the loop in a helper, `syncRelations(privFac)`, that runs `privFac.setRelationship(f.getId(), player.getRelationship(f.getId()))` for every faction. Call it on commission and once per day from `PrivateerLifecycleScript.advance` while a privateer is active. Then change `findHostileTarget` to test `privateer.getFaction().isHostileTo(f.getFaction())`, so the escort only targets fleets it will actually fight.

### B2 — The Underground Intel fallback can sell a mark on the far side of the sector
`src/skills_overhaul/corsair/UndergroundIntelService.java:171-179`
```java
FactionAPI faction = hostile.get((int)(Math.random() * hostile.size()));

SectorEntityToken anchor = null;
for (MarketAPI m : Global.getSector().getEconomy().getMarketsCopy()) {
    if (m.getFaction() == faction && m.getPrimaryEntity() != null) { anchor = m.getPrimaryEntity(); break; }
}
```
The faction is picked uniformly from every hostile faction that owns a market, and the anchor is the first such market in the economy list. Distance from the player is never checked. Two things contradict this:
- The ability tooltip (`UndergroundIntelAbility.java:90`, `"Queries the Underground for a profitable mark within 10 LY."`) and the CSV description promise a mark within 10 LY.
- `MarkIntel.advanceImpl` (`MarkIntel.java:33-35`) ends the intel once the mark has been more than 30 LY away for 7 days:
```java
if (distLY > 30f) {
    daysOutOfRange += Misc.getDays(amount);
    if (daysOutOfRange > 7f) endAfterDelay();
```

Failure scenario: the player is in a quiet frontier system with no hostile fleet in band. The roll falls back, and the spawned fleet appears at a hostile market 40 LY away. The player has paid 50 supplies (`COST_BASE`), and the intel expires before they could get there. Nothing is refunded, because the refund at `UndergroundIntelAbility.java:49-55` only covers `mark.fleet == null`.

Fix: choose the anchor by distance. Collect the hostile-owned markets, keep those within `SEARCH_LY` of the player (`Misc.getDistanceLY(playerFleet, m.getPrimaryEntity())`), and pick the nearest or a random one. Return `null` when none qualifies, so the existing refund path runs. Use the `rng` passed to `generateMark` rather than `Math.random()`, so the choice can be tested.

## Advisory

1. **The privateer payout counts kills it did not make.** `PrivateerLifecycleScript.java:50-65` sums `getDeploymentPointsCost()` of every member missing from each loser fleet on the losing side. It only needs the privateer to be somewhere on the winning side (`:42-45`). If a 25-FP privateer tags along in a large faction-vs-pirates fight near the player, the player is paid for the whole pirate loss, up to the 20,000-credit cap, once per battle for 30 days. Fix: scale the payout by the privateer's share of the winning side's strength at battle start. This is a balance issue with a ceiling, not a crash.
2. **The privateer lookup scans the whole sector on every frame once the privateer dies.** `LetterOfMarqueAbility.isUsable` (`:38-39`) calls `PrivateerFleetService.isCommissioned`. While `K_FLEET_ID` is still set, that calls `findPrivateerFleet`, which walks every fleet in every location (`PrivateerFleetService.java:58-62`). After the privateer is destroyed, `K_FLEET_ID` stays set until the expiry day (`PrivateerLifecycleScript.java:26-28`), so the ability bar's per-frame `isUsable` poll runs the full scan for up to 30 days. Fix: unset `K_FLEET_ID` and `K_EXPIRE` when the lookup finds the fleet dead or missing. `PrivateerEscortAI` already sees the death (`:50-53`) and could clear them.
3. **The black-market discount is written but never read.** `CorsairT0Handler.java:24` sets `$skills.corsair.bm_discount` to `0.05f`. A search of `src/` finds nothing that reads `K_BM_DISCOUNT` or the key. The Corsair T0 node therefore grants a discount that does nothing. Either wire it into a market listener or remove it.
4. **Six of the seven Infamy tiers do nothing.** Outside tests, `InfamyTier` is only used as `InfamyTier.LEGEND` (`UndergroundIntelAbility.java:30`, `:85`). KNOWN, WANTED, NOTORIOUS, FEARED, APEX and DREAD have no effect. Infamy is also recorded for every player, whether or not they own Corsair (`SkillsOverhaulModPlugin.java:88` registers `InfamyKillListener` unconditionally). This is harmless today, but an unlearned player's 30-day window would start pre-filled once more tiers are wired up.
5. **Saves from before e0b042d dismiss their privateer on load.** `K_EXPIRE` values written under the old `cycle*365 + getDay()` formula are smaller than the new `cycle*365 + DAY_OF_YEAR` values for the same date. A privateer active in such a save meets `today >= expireDay` (`PrivateerLifecycleScript.java:26`) right away and is despawned. The Infamy ring is cleared the same way: the gap jumps to 30 days or more and `InfamyService.java:36-38` zeroes it. This happens once per save.
6. **The day counter repeats a day after leap years.** `InfamyDailyTicker.monotonicDay` (`:28-29`) is `cycle*365 + DAY_OF_YEAR`. If `getCal()` is a Gregorian calendar with leap years, day 366 of cycle *c* and day 1 of cycle *c+1* both map to `365c+366`. The Infamy window then lasts 31 days once every four cycles, and expiry is one day late. Use `getCal().getTimeInMillis() / 86_400_000L`, or the clock timestamp the same way, instead. Not verified, because the calendar implementation is in the missing jar.
7. **The fallback in `InfamyKillListener` over-counts.** At `:28-30`, `catch (Throwable t) { fp = loserFleet.getFleetPoints(); }` credits the loser's whole remaining fleet when the destroyed and disabled lists throw. Use `fp = 0` and log the error instead.
8. **The same logic is written twice.** `UndergroundIntelService.cooldownActive`/`setCooldown` (`:58-78`) and the `InfamyService` `Map`/`MemoryAPI` overloads keep two copies of the same code. The 2026-07-07 audit names this drift pattern as the cause of its critical #1. `InfamyService.asMap` already shows the fix: one write-through view, with the logic written once.
9. **Fleet points and deployment points are mixed up.** `PrivateerLifecycleScript.java:61` adds `getDeploymentPointsCost()` into `destroyedFP` and calls `computePrivateerPayout(float destroyedFleetPoints)`, while `InfamyKillListener.java:25` uses `getFleetPointCost()`. Pick one unit and name it.

## Tests

1. **The two corsair "unit" tests copy the formula instead of calling it.** `InfamyKillListenerTest.stacks` (`:18-21`) and `UndergroundIntelAbilityTest.costFor` (`:48-51`) re-implement the logic, so they pass however production changes. Extract `InfamyKillListener.stacksFor(float fp)` and `UndergroundIntelAbility.costFor(Map, int)` and test those.
2. **The ring buffer's partial-rotation boundary is untested.** `InfamyServiceTest` checks a gap of 30 and a gap of over 30, but not the off-by-one edge: stacks recorded on day 0 must still count on day 29 and be gone on day 30 when every day in between is ticked. It also does not cover recording on several days and then skipping 10 days.
3. **There is no test for the `MemoryAPI` write-through bridge.** `InfamyService.asMap` must persist the cursor and the last day through `mem.set`, and mutate the stored `int[]` in place. A stub `MemoryAPI` (or a `Map`-backed test double) would catch a regression that silently stops Infamy from saving.
4. **B2 has no regression test.** Once the anchor is picked with `rng`, a distance filter over a plain list of (faction, distance) pairs can be unit-tested without the game.
5. **The strength-band boundary is ambiguous.** `inStrengthBand` (`UndergroundIntelService.java:42-44`) puts 0.85 and 1.15 in two bands each. This is harmless because one band is rolled first, but a test should state that intent.

## Design notes

1. A single shared `skills_overhaul_privateer` faction means every privateer, past and present, shares its relations. Deriving them from the player faction on every daily tick (B1) is simpler than keeping them up to date by hand.
2. `PrivateerLifecycleScript` is both a per-frame script and a campaign listener, registered as two transient objects on every load (`SkillsOverhaulModPlugin.java:93-96`). It only does daily work, so throttle `advance` to a day check like `InfamyDailyTicker`.
