Scope: every file in `src/skills_overhaul/commandant/` (10 files, 843 lines), `data/config/skills_overhaul/trees/commander_commandant.json`, the commandant rows in `data/campaign/abilities.csv` (rows 4-5) and `data/config/settings.json` (plugin rows 5, 7, 8), and the code on the other side of the area's boundary: the 14 commandant effect handlers in `effect/handlers/` (`SOCommandantT0Handler`, `SOCommandantT5Handler`, `SOCombatScriptHandler`, `SOCommandFieldModHandler`, `SOObjectiveScalingHandler`, `SOObjectiveCaptureBuffHandler`, `SODoctrineHierarchyHandler`, `SOOfficerInspirationHandler`, `SOFieldCommandsHandler`, `SOEliteCascadeHandler`, `SORefittingHandler`, `SOStandingOrdersHandler`, `SOInGoodHandsHandler`, `SOCommandAndConquerHandler`), `effect/AbilityGrants`, `state/NodeApplyService.resetTransientStatics`, `supply/SupplyBufferService.tryConsume`, and all 7 tests under `test/skills_overhaul/commandant/`. Base: `master` @ 63c6434.

Why this area: `reviews/` on master holds only triage files. The review branches on origin cover effect, ui, artificer, pilot, collective, zealot, corsair and data. `commandant` had never been reviewed and is the largest package that had not.

Not compiled: `build.sh` compiles against the game jars at `/home/jayden-eppcohen/Games/Starsector`, which are not in this container, and every commandant test imports a class that imports `com.fs.starfarer.api`. Engine behaviour (assignment object identity, ownership of dead hulls) is from base-game knowledge, not checked against the jar.

## Verdict

The combat side of the tree mostly does what it says. The defects are in coverage and stacking, not crashes. The three most valuable fixes: (1) wire or remove the four commandant nodes that cost 7 points and do nothing (Elite Cascade, War Room, Doctrine Hierarchy, Officer Inspiration). Three of them are Iron Doctrine prerequisites, so every capstone buyer pays for at least one dead tier-4 node (B2). (2) Add energy weapons to the Command Field aura. It boosts beams, ballistics and missiles but not energy projectile weapons, so the tier-0 core does nothing for pulse, ion or plasma loadouts (B1). (3) Key Field Commands buffs by fleet member and order type, not by assignment identity. As written, re-issuing an order to a ship stacks a second x1.20 Strike buff and a second +500 aura range on top of the first (B3).

## Blocking

### B1. Command Field never boosts energy projectile weapons
`src/skills_overhaul/commandant/CommandFieldListener.java:22-24`
```java
        ship.getMutableStats().getBeamWeaponDamageMult().modifyMult(STAT_KEY, 1f + totals[0]);
        ship.getMutableStats().getBallisticWeaponDamageMult().modifyMult(STAT_KEY, 1f + totals[0]);
        ship.getMutableStats().getMissileWeaponDamageMult().modifyMult(STAT_KEY, 1f + totals[0]);
```
Failure: a fleet of officered ships armed with pulse lasers, ion cannons or plasma cannons gets the defensive half of the aura (lines 25-27) but no damage bonus. Energy beams get it through the beam multiplier. Every other damage buff in the package (`CommandantCombatPlugin.java:97-98,107-108,140-141`, `FieldCommandsService.java:152-156`) uses `getEnergyWeaponDamageMult`, so this is an omission, not a design choice. The aura is the tier-0 core effect that the whole tree scales (Officer Training, Authority, Esprit, Iron Doctrine).
Fix: replace the beam line with `getEnergyWeaponDamageMult()`. If you also keep the beam line, energy beams double-dip.

### B2. Four nodes (7 skill points) have no effect, and the capstone gate forces buying one
The only readers of `CommandantCombatPlugin.ACTIVE_NODES` are `CommandantCombatPlugin.java:50` and `:72-79`, which test `commandant_t1_officer_training`, `_t1_drilled`, `_t2_authority`, `_t2_cohesion`, `_t2_reserve`, `_t3_line_anchor`, `_t3_vanguard` and `commandant_t5`. These handlers only add an id nothing reads, or set a memory key nothing reads (I grepped `src/` and `data/` for every key):
- `src/skills_overhaul/effect/handlers/SODoctrineHierarchyHandler.java:11`: `CommandantCombatPlugin.ACTIVE_NODES.add(nodeId);` (Doctrine Hierarchy, cost 2)
- `src/skills_overhaul/effect/handlers/SOOfficerInspirationHandler.java:11`: `CommandantCombatPlugin.ACTIVE_NODES.add(nodeId);` (Officer Inspiration, cost 2)
- `src/skills_overhaul/effect/handlers/SOObjectiveCaptureBuffHandler.java:12-13`: `CommandantCombatPlugin.ACTIVE_NODES.add(nodeId);` and `Global.getSector().getMemoryWithoutUpdate().set("$skills.commandant.war_room.officer_slot_bonus", 2);` (War Room, cost 2)
- `src/skills_overhaul/effect/handlers/SOEliteCascadeHandler.java:13`: `Global.getSector().getMemoryWithoutUpdate().set(K_PURCHASED, true);` (Elite Cascade, cost 1)

`data/config/skills_overhaul/trees/commander_commandant.json:121-128` gates Iron Doctrine on `"atLeast": 2` of the four tier-4 nodes. Only `commandant_t4_field_commands` has an effect.
Failure: a player heading for Iron Doctrine buys Field Commands plus one of War Room, Doctrine Hierarchy or Officer Inspiration and gets nothing for the second 2 points. A player who buys Elite Cascade gets nothing for 1 point. The tooltips sell these effects.
Fix: implement the four effects (a per-ship branch in `applyPerShipEffects` for the three combat ones; a reader of the War Room officer-slot key, which needs a campaign hook). If they cannot ship yet, mark them unpurchasable in the tree data and drop them from the T5 `of` list. Either way, add the data-consistency test in T1.

### B3. Field Commands buffs stack when an order is re-issued to the same ship
`src/skills_overhaul/commandant/FieldCommandsService.java:79`
```java

```
`:95-96`
```java

            applyBuffStart(key, typeName);
```
`:154-156`
```java
        } else if ("STRIKE".equals(typeName)) {
            s.getBallisticWeaponDamageMult().modifyMult(key, 1.20f);
            s.getEnergyWeaponDamageMult().modifyMult(key, 1.20f);
```
`:117-118`
```java

                CommandFieldService.SHIP_RANGE_BUMP_PREFIX + memberId, 500f);
```
The stat modifier id is the per-assignment key, and an old key's buff is removed only when its own timer runs out (`:99-100`). It is not removed when the ship leaves the assignment.
Failure: assign a cruiser to Strike order A, then within 20 s create Strike order B on another target and move the cruiser to it. The cruiser now carries `STRIKE:<A>:id` x1.20 and `STRIKE:<B>:id` x1.20 = x1.44 ballistic/energy damage, plus +1,000 aura range. Each re-issue inside the window multiplies again. The only limit is command points (four re-issues give x2.07). Only RETREAT has a once-per-ship guard (`:90-93`). If the engine hands out fresh `AssignmentInfo` objects for the same order, every 0.25 s tick creates new keys and the stacking has no limit. I could not check that without the game jar.
Fix: key buffs by `typeName + ":" + memberId`, so re-issuing refreshes the timer instead of adding a modifier. When a member's key leaves the snapshot, either keep the buff to the end of its window under that one key, or end it early, but never hold two keys of the same type for one member. Register the range bump under the same member-scoped key so it cannot sum.

## Advisory

1. **Paid effects with no reader.** These are partial no-ops on nodes that have other working effects: `SOCommandantT0Handler.java:17-19` sets `officer_market_freq`, `officer_xp_mult` and `officer_salary_mult` (the T0 base channel: officer XP +20%, salary -20%). `SORefittingHandler.java:13-14` sets `refitting.recovery_chance_bonus` and `refitting.dmod_avoid` (only the Craft abilities work). `SOObjectiveScalingHandler.java:14` sets `$skills.commandant.authority`. `SOCommandantT5Handler.java:15` sets `$skills.commandant.t5.purchased`. `SOCombatScriptHandler.java:17` sets `$so_commandant.tier_reached.3`. Nothing in `src/` or `data/` reads any of them. The T5 `"channel": "base"` effect (`commander_commandant.json:131`) runs the handler with no branch for `base`, so it does nothing.
2. **The commandant combat plugin runs in missions on stale campaign state.** `CommandantCombatPlugin.java:34-36` has no `isInCampaign()/isInCampaignSim()` guard, while `CommandFieldRegistrar.java:20` and `ZealotCombatPlugin.java:39` both have one. `ACTIVE_NODES` is a JVM static filled at load. After loading a save and returning to the menu, mission and title-screen battles give player ships Authority, Cohesion, Line and Anchor and the other buffs.
3. **Esprit de Corps scales the receiver's range, not the source's.** `CommandFieldService.java:111-112` picks the class bump from the hull of the ship *receiving* the aura (`computeEffectiveRange(hullOrdinal)` of `ship`). The Field Commands bump at `:128` comes from the *source* (`shipRangeBump(fm.getId())`). So a capital collects officers from 2,000u, while a capital's officer still projects only 1,500u to a frigate. The spec is not in the repo. Confirm which one is intended and make the two bumps use the same side.
4. **Fleet-member effects only cover the fleet as it was at apply time.** `SOStandingOrdersHandler.java:22-25` and `SOInGoodHandsHandler.java:26-35` loop over `getMembersListCopy()` once, on purchase or on load. Ships bought or recovered later get no CR-recovery bonus, and captain changes have no effect, until the next save load. In Good Hands says so in its javadoc (`:15`); Standing Orders does not.
5. **Per-frame O(n²) scans.** Tactical Cohesion, Line and Anchor and Vanguard Screen (`CommandantCombatPlugin.java:134,183,205`) each walk `engine.getShips()` for every player ship on every unpaused frame. On top of that, `CommandFieldService.computeTotalsForShip` (`:118`) does an O(n) scan per ship every 0.5 s, plus three linear scans of `PARAMS` per source (`shipRangeBump` at `:128`). In large battles with fighters in `getShips()` this adds up. Run them on a shared `IntervalUtil` as `CommandFieldListener` already does.
6. **Field Commands ticks with a fixed dt and ignores pause.** `FieldCommandsListener.java:19-21` advances the interval with `amount` and does not check `engine.isPaused()` (the commandant and zealot plugins do). The service is then ticked with a hard-coded `0.25f`. The modifier key uses `System.identityHashCode`, which is not unique. A collision between two orders that share a type and member would merge their buffs.
7. **The two craft abilities are copies.** `CraftFuelAbility.java` and `CraftSuppliesAbility.java` are line-for-line identical except for the id, output and the `addCommodity("fuel", …)`/`addSupplies(…)` line. A shared base class would remove most of the 67 duplicated lines, including the buffer-refund path. Also, with an empty buffer, Craft Supplies removes 10 fleet supplies and adds 10 back (`:38-40`): it does nothing but start the 2-day cooldown.
8. **Marching Advance leaves out missiles.** `CommandantCombatPlugin.java:97-98` buffs ballistic and energy only, while Drilled and Ready (`:107-109`) also includes missiles. The javadoc (`:84`) says "weapon damage". Align them or fix the javadoc.

## Tests

1. **No consistency test between node data and effect consumers.** Every node id that a handler adds to `CommandantCombatPlugin.ACTIVE_NODES` should be read by the plugin, and every `$skills.commandant.*` key should have a reader. `CommandantTreeLoadTest` checks layout and prereq references only. A test listing the plugin's handled ids against the tree's `SO_combat_script`, `SO_doctrine_hierarchy`, `SO_officer_inspiration` and `SO_objective_capture_buff` nodes would have caught B2.
2. **Field Commands re-issue behaviour is untested.** `FieldCommandsServiceTest` covers `diffNewlyIssued`, `tickBuffTimers` and `bufferDurationFor` in isolation. Nothing covers "same member, same type, new assignment refreshes and does not stack" (B3). Pull the snapshot-to-buff-key logic out of `tick` into a pure function and test it.
3. **The Command Field stat set is untested.** No test pins which damage multipliers the aura touches (B1). A small pure helper that returns the stat ids to modify would make it testable without the engine.
4. **Craft-ability tests only check constants.** `CraftAbilityCostTest` asserts six constants. The refund path when the fleet lacks supplies (`CraftFuelAbility.java:32-37`) lives inside `activateImpl` and has no test. Extract it.
5. **Iron Doctrine wiring is untested.** `IronDoctrineStateTest` covers the state machine, but nothing checks that `applyIronDoctrine` registers and unregisters `iron_doctrine_total`, or that `init` clears both params. `CommandFieldServiceTest.java:35` also carries a garbled assertion message ("…so sum=6%; wait — sum is 0.03+0.03=0.06") that should be rewritten.

## Design notes

1. Buffs apply to every `owner == 0` ship, including allied fleets in a joint battle (`CommandantCombatPlugin.java:53`, `CommandFieldRegistrar.java:26`). If the tree is meant to cover the player's own fleet only, filter on `getFleetMember()` belonging to the player fleet.
2. Two parameter registries coexist: `CommandFieldService.PARAMS` is a string-keyed bag queried by `endsWith`, and the meaning of each param lives in its readers. A typed holder with one field per param would remove the suffix-matching (and the prefix-collision risk in `unregisterParam`) and make dead params easy to see.
3. `ACTIVE_NODES` is filled by five different handler classes (`SOCombatScriptHandler`, `SODoctrineHierarchyHandler`, `SOOfficerInspirationHandler`, `SOObjectiveCaptureBuffHandler`, `SOCommandantT5Handler`, plus the `node` param indirection). One handler type with the node id as data would make it obvious which ids have a consumer.
