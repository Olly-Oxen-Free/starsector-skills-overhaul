## Verdict

I found no blocking defect in `state/`. Within the same JVM, `NodeApplyService.resetTransientStatics` clears every handler-populated static I could find: all eight `ACTIVE_NODES` sets, `CollectiveActiveNodes.ACTIVE`, the command-field params, the supply cap multipliers, forge unlocks, the free-deploy and automated-point bonuses, the bounty-board flags, `FieldCommandsService.active` and the salvage multipliers. The combat-scoped statics that the reset leaves alone (`FieldCommandsService.lastSnapshot/activeBuffs/retreatUsedThisBattle`, `FinalGambitService.triggered`, `TesseraMimicHullMod.spawned`, the Zealot and Corsair per-battle sets) are each cleared at combat init.

The three most valuable fixes:
1. **(A1)** Reconcile `$skills.purchased.*` flags whose node id no longer resolves to a loaded tree. Today they are skipped silently, so the points spent on them are stranded and their persistent side effects stay for good.
2. **(A2)** Stop one throwing handler from costing the player abilities. When a handler throws, `revokeUngranted` treats the abilities it had not yet granted as unowned and revokes them.
3. **(T1)** Add a test for `resetTransientStatics` and for applying a reload twice. The reset list is maintained by hand and has no coverage at all.

## Advisory

### A1. Owned nodes missing from the loaded trees are dropped silently: points are stranded and side effects are never removed

`src/skills_overhaul/state/NodeApplyService.java:43-45`
```java
            for (TreeDef def : trees) {
                for (Node node : def.getNodes()) {
                    if (!Boolean.TRUE.equals(mem.get(SkillMemory.purchasedKey(node.getId())))) continue;
```
Reapply visits only the nodes of the trees that loaded. Respec works the same way: `RespecRunner.java:30` (`for (TreeDef def : TreeRegistry.getTrees(tree))`) builds `ownedBefore` from those same trees, and `:72` unsets only the flags of those nodes.

So a save can hold a `$skills.purchased.<id>` flag plus its `$skills.spend_record.<id>.tl/.fu/.mg` records for a node that no loaded tree defines. Three things produce that:
- `TreeRegistry.install` drops a whole tree when one of its ids clashes with another tree (`TreeRegistry.java:44-50`).
- `TreeLoader` rejects a malformed tree file.
- A node id is renamed. This has happened before: commit `54a6087` replaced `pilot_systems_t0` / `pilot_systems_t5` with `so_systems_*`.

Failure scenario: the player buys Synaptic Relay, and a later update renames the node or its tree fails to load.
- On load, the node is not re-applied, and nothing logs it.
- Respec cannot see the node, so the points recorded for it can never be refunded.
- The persistent effects written by `apply()` stay in the save. These include the `so_neural_uplink` permamod (`pilot/systems/SynapticRelayService.java:21`, `member.getVariant().addPermaMod(HULLMOD_ID);`), `$skills.zealot.t5.purchased` (`effect/handlers/SOZealotT5Handler.java:15`) and the fleet fuel mults (`effect/handlers/collective/SOIntegratedLogisticsHandler.java:23-24`).

Fix: after the reapply loop, walk `mem.getKeys()` (already used in `suppress/VanillaSuppressor.java:58`) for `$skills.purchased.` keys that match no loaded node.
- Log each one by id.
- Refund its `RespecService.RECORD_PREFIX + id` records. The `.tl` share can go to the free universal pool, because the owning tree can no longer be identified.
- Unset the flag and the records.
- Optionally add a small rename map (`old id -> new id`) that is applied before the scan.

### A2. When a handler throws, `revokeUngranted` removes an ability the player owns

`src/skills_overhaul/state/NodeApplyService.java:49-55, 60`
```java
                    try {
                        skills_overhaul.effect.NodeEffectApplier.apply(node);
                        count++;
                    } catch (RuntimeException ex) {
```
```java
        skills_overhaul.effect.AbilityGrants.revokeUngranted();
```
`NodeEffectApplier.apply` (`effect/NodeEffectApplier.java:15-18`) runs a node's effects in order. If one of them throws, the later effects of that node never run. Any `AbilityGrants.grant(...)` call that would have come after the throw is skipped, and `revokeUngranted` (`effect/AbilityGrants.java:138-142`) then removes that ability from both character data and the fleet. The player loses an ability they paid for until a later load succeeds.

Separately, `resetTransientStatics()`, `revokeUngranted()` and `AutomatedShipCapApplier.applyToPlayerFleet()` are not guarded at all, and the per-node catch only covers `RuntimeException`. A `LinkageError` from an API mismatch, or any throw from those calls, ends `onGameLoad` at `SkillsOverhaulModPlugin.java:133`, so `OrphanSkillGranter.applyAllOnLoad()` at `:136` never runs.

Fix:
- Record the nodes whose apply threw, and skip `revokeUngranted` for the abilities those nodes own. The simplest version is to skip revocation entirely on any pass where something failed.
- Catch `Throwable` around each node, and around the three trailing calls, with a `warn` log.

### A4. The memory-key authority is split: the migration pool key is defined three times

`SkillMemory` documents itself as the place where keys are built, but the unallocated-migration pool key is written out as a literal in three places:
- `src/skills_overhaul/migration/MigrationPlugin.java:12`: `public static final String MIG_UNI_POOL_KEY = "$skills.points.universal_migrated_unallocated";`
- `src/skills_overhaul/level/SpendService.java:9`: `public static final String POOL_UNALLOC = "$skills.points.universal_migrated_unallocated";`
- `src/skills_overhaul/ui/view/SkillTreeView.java:403`: `String migK = "$skills.points.universal_migrated_unallocated";`

A typo in any one of the three desyncs the UI label, the migration grant or the spend path from the others, and the compiler cannot catch it. Add `SkillMemory.migPoolKey()` and point all three at it. The same applies to `POOL_LOCK_KEY`, `RespecService.RECORD_PREFIX` and `$skills.zealot.t5.purchased`.

### A5. The Map and MemoryAPI overloads in `SkillMemory` have drifted apart

`src/skills_overhaul/state/SkillMemory.java:38`
```java

```
This is a hard cast. A `Float` or `String` stored under the key throws `ClassCastException`, whereas the MemoryAPI twin (`:72`) uses `getBoolean`.

`:56-57`
```java
        java.util.List<String> empty = new java.util.ArrayList<>();
        m.put(activeBasicsKey(), empty);
```
This getter writes to the map while reading, and it returns the live list. The MemoryAPI read path (`basics/ActiveLaneService.java:87-90`) returns a copy and writes nothing.

`setPoints` (`:35`) has no MemoryAPI twin, so callers write the key by hand: `level/GameSpend.java:107` and `level/RespecRunner.java:63` both use `mem.set(SkillMemory.pointsKey(t), ...)`.

None of these is live today, because the Map overloads are reached only from tests and snapshots. They are traps for the next caller. Fix:
- Make the Map getters side-effect-free and copy-returning.
- Use `Boolean.TRUE.equals(v)` in `isMigrated(Map)`.
- Add `setPoints(MemoryAPI, ...)`.

## Tests

1. **`NodeApplyService` has no test.** Make `resetTransientStatics()` package-visible and test it without `Global`: fill every registry it names, call it, and assert that each one is empty or back at its default (`BountyBoardListener.weaponDropMult == 1f`, `FieldCommandsService.active == false`). This is the only guard on a hand-maintained list (see Design note 1).
2. **Idempotence and cross-save bleed.** With a map-backed fake memory, purchase nodes, run the reapply body twice, and assert that `ACTIVE_NODES`, `CommandFieldService.sumParam(...)`, the supply cap multiplier product and the forge unlocks match the result of a single pass. Then switch to a second fake save with no purchases and assert that everything is empty. This needs the reapply loop split away from `Global.getSector()`, the same way `GameSpend` is split from `SpendService`.
3. **Orphaned purchased keys.** Once A1 is fixed, add a test where a fake memory holds `$skills.purchased.ghost` plus records. Reconciliation should refund the points and unset both the flag and the records.
4. **`SkillMemoryTest` coverage gaps.** Missing-key defaults are checked only for XP. Level, points and migrated have no default checks. The test never touches `setPoints`, `getSupplyBuffer/setSupplyBuffer`, `getActiveBasics/setActiveBasics` (including the copy semantics of `setActiveBasics`), or the key strings themselves. Pinning `xpKey(PILOT).equals("$skills.pilot_xp")` and friends would catch a key change that breaks saves.

## Design notes

1. **The reset list is a hand-maintained registry.** `resetTransientStatics` (`NodeApplyService.java:69-97`) names 17 statics across 15 classes. Every new purchase-time registry must be added here by hand, or it leaks between saves in the same JVM, and that leak is exactly the bug the method was written to fix. A tiny `TransientRegistry.register(Runnable reset)` called from each registry's static initialiser removes the coupling. Test 1 then becomes trivial.
2. **Reapply is apply-only.** Load replays `apply()` over the current gating but never calls `remove()`. Anything persistent that an earlier `apply()` wrote (permamods, fleet stat mods, memory flags) is trusted to have been removed at respec or lane-change time. A1 is one case where it never is. A persisted ledger of applied node ids would let load diff that ledger against the owned set and call `remove()` for the difference.
3. **`Tree` constant names and keys are save format.** `Tree.key` appears in every memory key (`SkillMemory.java:7-13`), and `Tree.name()` is persisted in the pool lock (`level/SpendService.java:74`, `mem.put(POOL_LOCK_KEY, tree.name());`). Renaming either one silently breaks existing saves. Mark both as frozen in a comment on the enum.
