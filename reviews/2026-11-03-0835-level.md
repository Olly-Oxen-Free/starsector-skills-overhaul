## Verdict

The pure logic (`PurchasePlan`, `XPCurve`, `RespecService`) is small and mostly sound, but spending migrated points is broken. The three most valuable fixes:
1. **B1**: `SpendService.spend` credits migrated pool points to the tree's locked balance when it should consume them. Every migrated point buys two points of nodes, and a respec makes the doubled balance permanent.
2. **A1**: wrap `NodeEffectApplier.remove` in `RespecRunner` the way `GameSpend` wraps `apply`. Otherwise one throwing handler aborts the respec after the refund has been written: no story point is charged and the active-basics list keeps nodes the player no longer owns.
3. **A2/A3**: delete or align the two test-only code paths (`SpendService.refund` and `LevelService.reconcileFromXP`). Both disagree with the live code, and the tests pass against them, not against the live behaviour.

## Blocking

### B1. Migrated pool points are added to the tree balance instead of being spent: double spend, made permanent by respec

`src/skills_overhaul/level/SpendService.java:65-67`
```java
        // Pool points lock to this tree; add them to the tree-locked migration key
        mem.put(SkillMemory.migUniKey(tree), migLocked - takeML + takePool);
        mem.put(POOL_UNALLOC, migPool - takePool);
```
`takePool` points leave the unallocated pool and pay for the node, but they are also added to `migUniKey(tree)`. Step 2 of the next spend (`SpendService.java:43`, `int takeML = (int) Math.min(remaining, migLocked);`) then spends them a second time. `RespecService.respecTree` refunds the full recorded `.mg` amount into the same key (`RespecService.java:57`, `mem.put(SkillMemory.migUniKey(tree), f(mem.get(SkillMemory.migUniKey(tree))) + totalMig);`), so after the first (free) respec the doubled balance is real and permanent.

Failure scenario: a save that migrated 5 vanilla points, so `$skills.points.universal_migrated_unallocated = 5`. The player buys a 5-point batch in PILOT: the pool drops to 0 and `migUni(PILOT)` rises to 5. They buy another 5 points of nodes from `migUni(PILOT)`. Then they respec: `migUni(PILOT)` = 10. Reproduced with the stub harness:
```
after n1: ok=true pool=0.0 migPilot=5.0
after n2: ok=true migPilot=0.0
after respec: migPilot=10.0
```
This hits every upgraded save (`MigrationPlugin.runOnce(false)` grants the pool). The UI hides it: the "Migrated points" label reads only the unallocated pool (`SkillTreeView.java:403-407`), so the inflated `migUni(tree)` balance never appears on screen.

Fix: `mem.put(SkillMemory.migUniKey(tree), migLocked - takeML);`, and keep the lock write at `:70-72`. The lock is the only thing that should tie the pool to the tree; `RespecService` already returns refunded migration points to `migUni(tree)`, which is the right place once the spend stops crediting it. Add the assertion in **T1**. Saves that already spent pool points carry an inflated `migUni(tree)`. The original grant is not stored anywhere (`MigrationPlugin` writes it into the pool key, which spending then decrements), so an exact repair needs that grant to be stored first. Mention this in the changelog.

## Advisory

### A1. `RespecRunner` has no guard around effect removal; a throw leaves a half-done respec with the story point uncharged
`src/skills_overhaul/level/RespecRunner.java:79`
```java
        for (Node n : ownedBefore) NodeEffectApplier.remove(n);
```
By this point `:61-76` have already written the refund and cleared the purchased flags and records. If any handler's `remove` throws, three things are skipped: `ActiveLaneService.onUnpurchased` (`:82-84`), so unowned T0 ids keep both active slots and newly bought T0s never auto-activate (`ActiveLaneService.java:96`, `if (cur.size() < MAX_ACTIVE)`); the story-point charge (`:87-90`), so a paid respec becomes free; and the effect removal of every later node, whose effects stay applied until the next load. The exception also escapes `SkillTreeView.buttonPressed`. Fix: wrap each `remove` in a try/catch with the same logging `GameSpend.java:55-60` uses for `apply`, or charge and update the lane list before removing effects.

### A2. `SpendService.refund` is dead in production and contradicts the respec rule for migrated points
`src/skills_overhaul/level/SpendService.java:83-85`
```java
        // Return migration points to the unallocated pool (un-locking them from this tree)
        mem.put(SkillMemory.migUniKey(tree), f(mem.get(SkillMemory.migUniKey(tree))) - fromMigration);
        mem.put(POOL_UNALLOC, f(mem.get(POOL_UNALLOC)) + fromMigration);
```
Only `SpendServiceTest` calls it. It unlocks migrated points back to the shared pool, while the real refund path (`RespecService.java:57`) keeps them locked to the tree. Two rules for one concept mean anyone who wires up a per-node refund later inherits whichever one they happen to call. Delete it, or make it delegate to the respec rule.

### A3. `LevelService.reconcileFromXP` differs from the live `LevelReconciler`
`src/skills_overhaul/level/LevelService.java:36-37`
```java
        for (int lv = current + 1; lv <= target; lv++) processLevelUp(mem, tree, lv, cfg);
        SkillMemory.setLevel(mem, tree, target);
```
The unconditional `setLevel(target)` lowers the level when XP is below the stored level, without taking points back. A later climb then grants the same levels' points again. `LevelReconciler.java:30-36` never lowers the level. Only tests call `reconcileFromXP` (`LevelServiceTest.java:34`, `RoundTripTest.java:22`), and `LevelServiceTest` asserts exactly this downgrade (level 8 → 5). The tests therefore exercise behaviour the game never runs. Make `LevelReconciler` call one shared `MemoryAPI`/`Map` routine, and drop the downgrade.

### A4. The XP readout keeps counting past the level cap
`src/skills_overhaul/ui/view/SkillTreeView.java:440-441`
```java
        long req = XPCurve.xpForLevel(level + 1);
        long cur = xp - XPCurve.cumulativeXP(level);
```
At level 25 `xpForLevel(26)` is still a positive requirement (`XPCurve.java:8-11` has no cap check), so the bar shows progress toward a level 26 that `levelFromXP` (`XPCurve.java:29-34`) never grants, and `cur` is not clamped to `req`. Return 0 from `xpForLevel` for `level > LEVEL_CAP`, or have the view show "max".

### A5. Duplicated snapshot / write-back code between `GameSpend` and `RespecRunner`
`GameSpend.java:75-94` and `105-122` and `RespecRunner.java:38-76` each hand-copy points, pools and records between `MemoryAPI` and a map, and the record suffixes are spelled out three times (`GameSpend.java:117`, `RespecRunner.java:52`, `RespecRunner.java:73`: `new String[]{".tl", ".fu", ".mg"}`). `RespecService` owns the record format (`recordPurchase`, `RECORD_PREFIX`) but not the suffix list. A new pool or record field has to be added in five places. Move the key list and the copy routines into one class.

### A6. Stale or dead code
- `XPCurve.java:13`: `/** Precomputed cumulative thresholds — levelFromXP runs 3×/sec in LevelReconciler. */`. `LevelReconciler.java:18-20` runs once per second.
- `state/Tree.java:12`: `nodeIdPrefix()` has no callers. `RespecService.java:38-42` describes it as the cause of an earlier zero-refund bug. Delete it so nobody filters by it again.
- `LevelReconciler.java:26-36` posts one campaign message per level gained. A save whose XP jumps several levels at once posts several messages in the same frame; one summary message would do.

## Design notes

1. Points are stored in sector memory as `float` and read back with `(int)` truncation (`SkillMemory.java:70-71`, `SpendService.java:43,48,53`). Every value is a whole number today, but a fractional grant (an XP multiplier feeding points, or a config typo) would be lost silently. Store ints, or round on read.
2. `SpendService` has three migration fields (`fromMigrationToPilot/Commander/Admin`) that every caller adds back together (`GameSpend.java:47-48`, `PurchasePlan.java:117-118`). One `fromMigration` field plus the tree already known to the caller would do.
3. The pool lock is a bare string (`POOL_LOCK_KEY`) compared against `tree.name()`. If the `Tree` enum is ever renamed, the lock in old saves never matches again; a stable key such as `tree.key` would avoid that.
4. `GameSpend.commit` writes all pools back after each node (`:51`). That is correct but makes N full write-backs per batch; one write-back after the loop gives the same result, provided effect handlers keep their hands off the point keys (they do today).
