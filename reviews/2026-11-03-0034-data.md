# Deep review: `data` (2026-11-03-0034)

Scope: every file under `data/` (24 files, 2,266 lines): `data/config/settings.json`, `data/config/skills_overhaul.json`, the three tab indexes and 13 tree files under `data/config/skills_overhaul/trees/`, `data/campaign/{abilities,special_items,rules}.csv`, `data/hullmods/hull_mods.csv`, `data/world/factions/{factions.csv,skills_overhaul_privateer.faction}`, and `mod_info.json`. I also read the code that consumes this data: `tree/TreeLoader`, `TreeRegistry`, `TreeDef`, `Node`, `Prereq`, `PrereqValidator`, `config/Config` and `ConfigLoader`, `effect/EffectRegistry` and `NodeEffectApplier`, the generic stat handlers (`SOPilotedStatHandler`, `SOFleetStatHandler`, `corsair/StatBonusHandler`, `DModDpScalingHandler`, `SalvageMultiplierHandler`, `SOCommandFieldModHandler`), every T0/T5 handler, `level/SpendService`, `level/PurchasePlan`, `ui/view/NodeTooltipContent`, the `SkillTreeView` load path, and `test/skills_overhaul/tree/TreeLoaderRealJSONTest`.

I checked the tree data with a script: global id uniqueness, coordinate rules, prereq resolution and direction, registered effect types, `node` params, recipe ids, settings.json plugin classes and ability ids. Every class in `settings.json` `plugins` exists and extends `BaseEveryFrameCombatPlugin`. Every `recipeId` exists in `ForgeRecipeRegistry`. Every key in `skills_overhaul.json` is parsed and read. Findings that earlier reviews already reported are marked as such and not counted again as new.

Build: `build.sh` hard-codes `GAME_DIR=/home/jayden-eppcohen/Games/Starsector`, and no `starfarer.api.jar` or `json.jar` exists in this container, so neither `build.sh` nor `build.sh test` was run. Nothing was compiled.

## Verdict

The tree files are structurally sound: no duplicate ids or coordinates, no dangling prereqs, and every effect type is registered. What is wrong is which data reaches the player. The three most valuable fixes: (1) add `"collective"` to `commander_index.json`, or delete the tree. The Collective tree's file, its 22 handlers, 30 classes and a combat plugin that runs every battle all ship, but the tree has never been loaded (B1). (2) Hide the Admin tab or keep it out of the migration pool until it has content. Its four T0 nodes do nothing, buying one can lock the shared migration pool to Admin, and its four capstones can never be bought (B2). (3) Give Air Superiority an effect that works, or move Carrier Command's prerequisite. Air Superiority's three params are all skipped, and it is the only way to reach Carrier Command (B3).

## Blocking

### B1. The Collective tree never loads: it is missing from the commander index
`data/config/skills_overhaul/trees/commander_index.json:1`
```json
{ "trees": ["corsair", "commandant", "zealot", "artificer"] }
```
`TreeLoader.loadAllForTab` (`src/skills_overhaul/tree/TreeLoader.java:79-88`) loads only the keys listed in `<tab>_index.json`, and `commander_collective.json` is not listed. `git log` shows the index has had this one line since it was created (7d83e8e), so the Collective tree has never loaded. Its file is valid: I ran the loader's rules over it (22 nodes, coordinates, prereqs, registered types) and they pass, so adding the key would load it. Its combat plugin is still registered and runs every battle:
`data/config/settings.json:13`
```json
"skills_overhaul_collective_combat":"skills_overhaul.collective.CollectiveCombatPlugin",
```
**Failure:** a player opens the Commander tab and sees four trees. No `so_collective_*` node can be bought, so `CollectiveActiveNodes.isActive(...)` (`src/skills_overhaul/collective/CollectiveCombatPlugin.java:99`) is always false. The feature is unreachable, but its classes and per-battle plugin ship anyway. `TreeLoaderRealJSONTest` iterates only indexed keys (`test/skills_overhaul/tree/TreeLoaderRealJSONTest.java:15-19`), so the test suite cannot catch this. The 2026-11-02-1235 collective review did not mention it.
**Fix:** if Collective is meant to ship, change the index to `["corsair", "commandant", "zealot", "artificer", "collective"]`. The layout code already sizes columns from the list (`SkillTreeView.java:203-208`). Fix the collective review's blocking items first, since they become live the moment the tree loads. If it is not meant to ship, remove the `settings.json:13` registration. Either way, add the index-coverage test (Tests #1).

### B2. Admin tab: T0 nodes do nothing, capstones can never be bought, and a purchase can lock the migration pool
`data/config/skills_overhaul/trees/admin_warden.json:4-17` (the same shape at the same lines in `admin_merchant.json`, `admin_prospector.json`, `admin_steward.json`)
```json
      "id": "admin_warden_t0",
      "name": "Warden",
      "desc": "Placeholder T0 — content TBD.",
      "x": 2, "y": 0, "cost": 1,
      "prereqs": []
    },
    {
      "id": "admin_warden_t5",
      "name": "Warden Capstone",
      "desc": "Placeholder capstone — content TBD.",
      "x": 2, "y": 5, "cost": 1,
      "prereqs": [{"all": ["admin_warden_t0"]}]
```
These nodes have no `effects`. The T5 node sits at y=5, but every purchase goes through the tier gate, which requires an owned or pending node at y-1:
`src/skills_overhaul/tree/PrereqValidator.java:44`
```java
        if (!hasAnyInPreviousTier(def, n.getY(), effective)) return Check.TIER;
```
No admin tree has a y=4 node, so `PurchasePlan.java:102` (`if (c == PrereqValidator.Check.TIER) return Result.fail(id, Reason.TIER, 0, m);`) always rejects every admin capstone. The tooltip reads "Blocked: need a node in the previous tier", which no purchase can satisfy. Buying a T0 node is allowed, and when the player has no Admin points it draws from the shared migration pool and locks the pool to Admin:
`src/skills_overhaul/level/SpendService.java:70-72`
```java
        if (takePool > 0 && lockedTo == null) {
            mem.put(POOL_LOCK_KEY, tree.name());
        }
```
**Failure:** a player migrates a save, opens the Admin tab and buys "Warden". Nothing happens, and from then on the remaining migration pool can be spent only on Admin, where nothing else can be bought. Pilot and Commander purchases can no longer use the pool until the player respecs. README line 34 says admin effects are not implemented yet, but the pool lock and the unbuyable capstones are defects in what ships.
**Fix:** until admin content lands, leave Admin out of the tab strip and out of `SpendService`'s pool (or drop the four admin trees from `admin_index.json` and skip empty tabs). When content lands, make sure every tree has a node at every tier from 0 to 4. Add the completability test (Tests #2).

### B3. Air Superiority is fully inert and is the only prerequisite for Carrier Command
`data/config/skills_overhaul/trees/pilot_systems.json:136`
```json
        { "type": "SO_piloted_stat", "bomberDamageVsCruiserCapital": 0.30, "interceptorSpeedBonus": 0.30, "interceptorDamageVsFighters": 0.25 }
```
`SOPilotedStatHandler.applyKey` sends all three keys to the log-and-skip branch:
`src/skills_overhaul/effect/handlers/SOPilotedStatHandler.java:158-161`
```java
            case "bomberDamageVsCruiserCapital": case "interceptorSpeedBonus":
            case "interceptorDamageVsFighters":
                Global.getLogger(SOPilotedStatHandler.class)
                        .info("[SO] param '" + key + "' handled in combat plugin or no direct API, skipping static apply");
```
No other file in `src/` reads these keys or the id `so_systems_air_superiority`, so the comment's "handled in combat plugin" is not true. The node is also the only way into Carrier Command:
`data/config/skills_overhaul/trees/pilot_systems.json:170`
```json
      "prereqs": [{ "all": ["so_systems_air_superiority"] }],
```
**Failure:** a player who wants Carrier Command (T4) has to spend a point on Air Superiority, which changes nothing in combat. The 2026-11-01-2306 effect review (advisory 10) noted that the node is mostly inert. The forced spend to reach Carrier Command is new here.
**Fix:** implement the three keys, for example in `SystemsCombatPlugin` as damage modifiers on fighters that belong to the player's ship, or replace them with keys that `applyKey` supports. Until then, move Carrier Command's prereq to `so_systems_strike_coord`.

## Advisory

1. **No node in any loaded tree has a description, so every tooltip shows raw handler ids.** None of the 170 nodes in the nine loaded commander and pilot trees has `"desc"`, and no effect has `"description"`. `NodeTooltipContent.build` falls back to the type string (`src/skills_overhaul/ui/view/NodeTooltipContent.java:57-58`: `String text = e.optString("description", ""); if (text.isEmpty()) text = e.optString("type", "");`). Hovering a node shows lines such as `SO_piloted_stat` or `SO_corsair_combat_script`, so the player cannot tell what a node does before paying for it. The admin trees, the only ones with `desc`, show "Placeholder T0 — content TBD." Add `desc` to every node, and make the data lint (Tests #3) fail when it is missing.
2. **Corsair Makeshift Operations does nothing, and Derelict Operations loses half its effect.** `commander_corsair.json:39`: `{ "type": "SO_corsair_dmod_dp", "dpPerDMod": 0.0, "crPenaltyMod": -0.50, "cap": 5 }`. `DModDpScalingHandler` reads only `cap`, `armorPerDMod` and `hullPerDMod` (`DModDpScalingHandler.java:27-29` in the handler, the header comment at :17-19 says `dpPerDMod` is ignored), and no file reads `crPenaltyMod`. Line 57 (`"dpPerDMod": -0.06`) is likewise ignored. Already reported in the effect review (advisory 11) and still on master. On the data side, either give Makeshift an effect a handler implements or mark it unpurchasable.
3. **Partly inert pilot nodes.** In each of these, at least one param goes to the skip branch at `SOPilotedStatHandler.java:151-161`: `pilot_defense.json:37` (`weaponHPBonus`, `fighterBayHPBonus`), `:46` (`moduleRepairMult`), `:55` (`crDeclineStart`, `crRegenInCombat`; only `pptBonus` applies), `:82` (`massMult`, `collisionDamageDealt`, `weaponHPBonus`; only `engineHPBonus` applies), `pilot_systems.json:37` (`ecmRatingBonus`, `enemyAccuracyReduction`). Already reported in the effect review (advisory 10). Listed here because the fix is either data (drop the keys) or handler (implement them), and the data side has not changed.
4. **`abilities.csv` declares all eight abilities `TOGGLE`, but every plugin class extends `BaseDurationAbility`.** Examples: `data/campaign/abilities.csv:2` (`Underground Intel,skills_overhaul_underground_intel,TOGGLE,,,,,,,FALSE,...`) and `UndergroundIntelAbility extends BaseDurationAbility`. Rows 2-7 also leave every timing column blank. Row 2 names `ui_underground_intel_on`/`ui_underground_intel_off` as UI sounds, but the mod defines no sounds (there is no `data/config/sounds.json`). Not verified against the game: whether a blank-timing duration ability with a `TOGGLE` spec activates and ends cleanly, and whether an unknown sound id only logs or throws. Check in game, or set `type` to match the class and either fill the timing columns or rely on code-side cooldowns.
5. **`SO_defense_carrier_supremacy` is registered but no node uses it.** `src/skills_overhaul/effect/EffectRegistry.java:93`: `handlers.put("SO_defense_carrier_supremacy",`. No tree file contains that type. Either a defense node lost its effect or the handler is dead code. The validator found no other registered-but-unused type outside the unloaded Collective tree.
6. **The `"base"` effect entries on all four commander capstones are dead data.** Examples: `commander_corsair.json:132` (`{ "type": "SO_corsair_letter_of_marque", "channel": "base" }`), `commander_commandant.json:131`, `commander_zealot.json:412-413`, `commander_artificer.json:490-491`. `NodeEffectApplier.shouldApply` ignores `channel` for nodes off T0 (`NodeEffectApplier.java:62-66`), so both entries run. The T5 handlers act only on `"core"` and default to `"core"` (for example `LetterOfMarqueHandler.java:10`), whereas the T0 handlers default to `"base"`. Today the base entry is a no-op. Anyone who deletes the "core" line thinking "base" is the main effect silently disables the capstone. Remove the base entries, or have `TreeLoader` reject `channel` on nodes whose y is not 0.
7. **The special item icon points at another mod's file.** `data/campaign/special_items.csv:2` uses `graphics/icons/cargo/IndEvo_consumable_missile_pulse.png`, which is not in this repo, and Industrial Evolution is not a dependency in `mod_info.json`. Already reported in the artificer review (advisory 1) and still on master.

## Tests

1. **Index coverage (would have caught B1).** Every `data/config/skills_overhaul/trees/<tab>_<key>.json` except `<tab>_index.json` appears in its tab's index, and every index key has a file. It fits as one more loop in `TreeLoaderRealJSONTest`.
2. **Tree completability (would have caught B2).** For every loaded tree, simulate buying nodes in y order through `PrereqValidator.check` with an unlimited budget, and assert that every node, the capstone included, is reachable. This covers the tier gate as well as the prereq clauses.
3. **Data lint (would have caught B3, advisory 1 and advisory 5).** Every effect `type` is a key in `EffectRegistry`, every registered type is used by some node, every `SO_piloted_stat` key has an applying branch rather than the skip branch, and every node has a non-empty `desc`. `EffectRegistry`'s handler map is static and package-private, so the test needs a small accessor or has to parse the source as my script did.
4. **Plugin and ability wiring.** Every `settings.json` `plugins` class loads and is an `EveryFrameCombatPlugin`. Every `abilities.csv` `plugin` class exists, and its `ABILITY_ID` equals the row's `id`. All are true today; nothing keeps them true.
5. **Capstone channel rule.** `TreeLoader.fromJSON` rejects (or the lint flags) `channel` on nodes whose y is not 0 (advisory 6).

## Design notes

1. Effects use two parameter schemas: `SO_piloted_stat` puts stat keys at the top level of the effect object, while `SO_fleet_stat` and `SO_corsair_stat_bonus` use a `stats: [{key, value}]` array. Both handlers silently log unknown keys. A single schema with one key whitelist per handler, checked at load time by `TreeLoader`, would make typos and unimplemented params fail at startup instead of in a log line.
2. Costs and capstone rules differ by tab with no stated reason: pilot T4 nodes cost 1 and pilot capstones 2, commander T4 nodes cost 2 and capstones 3. Commander capstones need `atLeast 2` of 4 T4 nodes, but the unloaded Collective capstone needs all 5 (`commander_collective.json`, `so_collective_transspatial_mind`). Settle the rule before Collective is indexed.
3. Every node falls back to the same icon (`Node.java:71`, `graphics/icons/skills/combat.png`) because no node sets `icon`. I could not check that this vanilla path exists. `SkillTreeView.preloadSprites` swallows a load failure, so a wrong path would show blank icons rather than crash.
4. Two nodes have prereqs in their own tier (`so_maneuver_deep_vent` → `so_maneuver_vent_sprint` at y=2, `so_maneuver_battle_focus` → `so_maneuver_perfect_timing` at y=4). The loader allows this and the tier gate still holds, but it is the only exception to the "prereqs point up" pattern. Document it in the tree schema or remove it.
