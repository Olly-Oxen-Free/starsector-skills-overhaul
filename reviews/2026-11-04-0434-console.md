## Verdict

Both console entry points fail to do what the README and CHANGELOG tell players they do. The documented orphan grants are no-ops: `grant("impact_mitigation")` routes through a handler that does nothing outside combat and is never re-run by the combat plugin, and `grant("carrier_supremacy")` adds a node id that no combat plugin reads. `prepareUninstall()` restores vanilla skill levels, but it leaves every save-serialised mod object in place (the `SeasonedCrewBarEvent` creator that every save gets, granted abilities whose plugins are mod classes, the `so_neural_uplink` perma-mod, `MarkIntel`, `PrivateerEscortAI`). The README's "save, then disable the mod" procedure therefore leaves a save that depends on the mod's classes. The three most valuable fixes, in order:
1. Make `prepareUninstall()` strip the mod-owned persistent objects, or stop telling players that removing the mod is safe.
2. Make the orphan grants reach combat. Either have `SkillsOverhaulCombatPlugin` also iterate granted orphans, or add the missing `so_defense_carrier_supremacy` branch to `DefenseCombatPlugin`.
3. Route console output through the Console Commands output channel, or log it, so players can see the "SAVE THE GAME NOW" instruction and the "Unknown …" errors.

## Blocking

### B1. Orphan grants for both documented skills have no gameplay effect
`src/skills_overhaul/console/OrphanSkillGranter.java:70-79`
```java
            new OrphanSpec(
                    "impact_mitigation",
                    "so_defense_impact_mitigation",
                    "SO_piloted_stat",
                    buildJSON("hitChance", 0.50, "damageReduction", 0.25)),
            new OrphanSpec(
                    "carrier_supremacy",
                    "so_defense_carrier_supremacy",
                    "SO_defense_carrier_supremacy",
                    new JSONObject())
```
- **Impact Mitigation.** `applyHandler` calls `SOPilotedStatHandler.apply`, which exits immediately in the campaign, where `runcode` is normally run and where `applyAllOnLoad` always runs: `src/skills_overhaul/effect/handlers/SOPilotedStatHandler.java:27-28` `ShipAPI ship = getPlayerShip(); if (ship == null) return;`. The only per-combat application path is `src/skills_overhaul/effect/SkillsOverhaulCombatPlugin.java:59-62`. It iterates `TreeRegistry.getTrees(Tree.PILOT)` nodes and skips any node without `SkillMemory.purchasedKey(...)`. `so_defense_impact_mitigation` is in no tree JSON, and `grep` finds it only in `OrphanSkillGranter`, so the 25% hull damage reduction is never applied in any battle.
- **Carrier Supremacy.** `src/skills_overhaul/effect/handlers/defense/SODefenseCarrierSupremacyHandler.java:12-15` adds the id to `DefenseCombatPlugin.ACTIVE_NODES` and applies the fighter refit modifier only when `getPlayerShip()` is non-null, which it is not in the campaign. `DefenseCombatPlugin` has no `ACTIVE_NODES.contains("so_defense_carrier_supremacy")` branch; `grep -rn so_defense_carrier_supremacy src` returns only the granter. The node is a marker that nothing reads.
- **Failure scenario.** A player follows CHANGELOG.md:29-30 and runs `grant("carrier_supremacy")`. The console prints `Granted: carrier_supremacy`, the memory flag persists, and every later battle plays exactly as it would without the grant. If the player runs the command *during* a battle, the stat applies to the current flagship for that one battle only, which makes the behaviour look intermittent.
- **Fix.**
  - In `SkillsOverhaulCombatPlugin.applyPilotSkills`, after the tree loop, also apply every orphan whose `$so_orphan_<name>` flag is true. This needs a package-visible accessor on `OrphanSkillGranter` that returns `(nodeId, effectType, params)` for granted orphans, plus a matching `removeFrom` on ship change.
  - For Carrier Supremacy, either change its spec to `SO_piloted_stat` with a fighter-refit key, or add a `so_defense_carrier_supremacy` branch to `DefenseCombatPlugin` that applies `getFighterRefitTimeMult().modifyMult(..., 0.80f)` to the flagship.

### B2. `prepareUninstall()` leaves mod-class objects in the save that the README says is safe to load without the mod
`src/skills_overhaul/console/UninstallHelper.java:21-28`
```java
    public static void prepareUninstall() {
        Global.getSector().getMemoryWithoutUpdate()
                .set(VanillaSuppressor.K_SUPPRESSION_DISABLED, true);
        VanillaSuppressor.restoreAll();
        System.out.println("Vanilla skills restored; suppression disabled.");
        System.out.println("SAVE THE GAME NOW, then disable Skills Overhaul in the launcher.");
```
The method only touches skill levels. These objects persist in the sector and are left behind:
- `src/skills_overhaul/SkillsOverhaulModPlugin.java:116-117`: `BarEventManager.getInstance().addEventCreator(new SeasonedCrewBarEvent());` runs for every game. The comment at :114 confirms "The creator is saved with BarEventManager", so every save holds an instance of a mod class.
- `src/skills_overhaul/effect/AbilityGrants.java:43,46`: `addAbility(abilityId)` puts the abilities from `data/campaign/abilities.csv` on the character and fleet. Their plugins are mod classes such as `skills_overhaul.corsair.UndergroundIntelAbility` and `skills_overhaul.artificer.alphastorm.AlphaStormAbility`.
- `src/skills_overhaul/pilot/systems/SynapticRelayService.java:21`: `member.getVariant().addPermaMod(HULLMOD_ID);` (`so_neural_uplink`).
- `src/skills_overhaul/corsair/UndergroundIntelAbility.java:59`: `addIntel(intel)` (`MarkIntel`).
- `src/skills_overhaul/corsair/PrivateerFleetService.java:95`: `privateer.addScript(new PrivateerEscortAI(privateer));`, plus a fleet whose faction is `skills_overhaul_privateer`.

**Failure scenario.** A player follows README.md "Uninstall" steps 1–3. On the next launch without the mod, the save still references `skills_overhaul.barevents.SeasonedCrewBarEvent`, which every save has, and possibly the other classes above. Starsector deserialises the whole sector graph, so the save cannot resolve those classes. The usual result is a failed load. At best, data such as abilities and hullmods silently disappear. I could not test this in-engine (no game install here); it follows from the comment at `SkillsOverhaulModPlugin.java:114` and Starsector's XStream save format.

**Fix.** `prepareUninstall()` should:
- remove `SeasonedCrewBarEvent` creators from `BarEventManager.getInstance().getCreators()`;
- call `AbilityGrants.revoke` for every id in its managed set;
- call `SynapticRelayService.remove()`;
- end and remove `MarkIntel` instances;
- despawn the privateer fleet whose id is in `K_FLEET_ID`;
- unset `$so_*` / `$skills.*` memory keys that hold non-primitive values.

Until then, README.md should say the mod is not save-removable.

## Advisory

1. **Console output is invisible to players.** Both files report only through `System.out.println`, for example `OrphanSkillGranter.java:29`, `:34`, `:116` and `UninstallHelper.java:25-27`. Console Commands' `runcode` does not echo stdout to the in-game console overlay, so the output goes to the launcher's stdout or log. The critical "SAVE THE GAME NOW…" instruction and every "Unknown orphan skill" or "Unknown market id" error are therefore never seen. Use `Global.getLogger(...)` plus a visible channel: `Global.getSector().getCampaignUI().addMessage(...)` in the campaign, or `org.lazywizard.console.Console.showMessage` behind a reflection guard to avoid a hard dependency. Engine behaviour not verified in-game.
2. **`fireCrisis` reports success when nothing happened.** `OrphanSkillGranter.java:115-116`
   ```java
           new skills_overhaul.xp.AdminXPTracker().onCrisisResolved(crisisType, m);
           System.out.println("Crisis fired: " + crisisType + " on " + marketId);
   ```
   `AdminXPTracker.onCrisisResolved` (`xp/AdminXPTracker.java:55-59`) returns silently for any type outside `CRISIS_VALUES` (`luddic_path_cell`, `pirate_base`, `hegemony_inspection`) and while the 365-day per-market cooldown is set. A typo such as `"pirate"` prints "Crisis fired". The method also accepts any market, including ones the player does not own; only the XP modifier changes. Return a boolean or awarded XP from `onCrisisResolved` and print that.
3. **Unreachable "no handler" branch.** `OrphanSkillGranter.java:59-61`
   ```java
           EffectHandler h = EffectRegistry.get(s.effectType);
           if (h != null) h.apply(s.nodeId, s.params);
           else System.out.println("No handler registered for " + s.effectType);
   ```
   `EffectRegistry.get` never returns null (`effect/EffectRegistry.java:221`: `return h != null ? h : NoOpHandler.INSTANCE;`). A mistyped `effectType` would therefore log a `NoOpHandler` warning reading `p.optString("type")`, which is empty here because the orphan params carry no `type` key, and the console would still say "Granted". The `h != null` check in `revoke` (:43-44) is also dead.
4. **Continuing to play after `prepareUninstall()` stacks vanilla and overhaul skills.** After the call, `K_SUPPRESSION_DISABLED` makes `VanillaSuppressor.applyOnEveryLoad` return early (`suppress/VanillaSuppressor.java:53`). `NodeApplyService.reapplyAllOwned()` still re-applies every purchased SO node on every load. A player who runs the command and keeps the mod enabled gets restored vanilla skills plus the full overhaul tree. The command is console-only, so this is a cheat vector rather than an exploit, but nothing warns about it or blocks it. Have `prepareUninstall` also suspend `reapplyAllOwned`, or print that the save is meant to be uninstalled immediately.
5. **`grant`/`revoke` do not check current state.** `grant` re-applies even when the orphan is already granted, and `revoke` calls `remove` even when it was never granted. Neither is harmful with the current handlers, which use id-keyed modifiers and set semantics. But there is no way to list orphans or their state (`lookup` is private and names are case-sensitive), so a player cannot see which orphans exist or which are granted. Add a `list()` entry point.
6. **`buildJSON` swallows errors.** `OrphanSkillGranter.java:84-86` `} catch (Exception e) { /* ignore */ }`. A non-String key would throw `ClassCastException` inside the loop, silently truncate the params and ship a partial effect. With static literal inputs, fail fast instead.
7. **`fireCrisis` is in the wrong class.** `fireCrisis` (`OrphanSkillGranter.java:103-117`) is an admin-XP debug hook placed in the orphan-skill class, and it uses fully qualified names instead of imports. Move it to a `console/AdminDebug` class.

## Design notes

1. The orphan mechanism duplicates node ownership outside the tree model (`$so_orphan_<name>` instead of `SkillMemory.purchasedKey`). Every consumer that iterates tree nodes misses orphans: the combat plugin, respec, the UI, and NodeEffectApplier's lane and oath gating. A cleaner model is a hidden `orphans` tree or node list in `TreeRegistry`, with `grant` setting `purchasedKey` so all existing paths pick them up.
2. Impact Mitigation's `damageReduction: 0.25` maps to `getHullDamageTakenMult()` (`SOPilotedStatHandler.java:79`). That is universal hull DR, not the "frag/explosive DR" described in the comment at `:143-145`. Once B1 is fixed, this becomes a strong off-tree defensive bonus that stacks with Fortify and Death's Door, up to the 95% clamp described in CHANGELOG. Decide whether that is intended.
3. Uninstall safety is a cross-cutting contract. Each feature that adds persistent objects (bar events, abilities, hullmods, intel, scripts, factions) should register a cleanup with one `UninstallRegistry` that `prepareUninstall` drains. A single hand-maintained method will drift.
